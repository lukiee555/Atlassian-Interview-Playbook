AI code-design sequence

Map—do not edit

Do not modify files. Trace the reported behavior from entry point through validation, service/domain, persistence and error mapping. Cite exact paths and symbols, identify every mutation path, relevant tests and commands, and mark inferences.

Plan the smallest safe change

Do not implement. Propose the smallest repository-consistent change: files and symbols, authoritative placement, error behavior, edge cases, tests, assumptions, security and rollback risk. Avoid dependencies and unrelated refactors.

TDD RED - prove the next behavior

Do not modify production code. Using the confirmed acceptance criterion and this repository's existing test conventions, add the smallest focused test that must fail under current behavior. Run only that test, show the exact failure and stop. If it passes, investigate the existing implementation or test path instead of editing blindly.

TDD GREEN - minimum change

The focused test fails for the expected reason. Implement only the minimum production change required to make it pass, preserving interfaces, error contracts and repository conventions. Show the diff and focused test result before adding another requirement.

P40 LLD selector

Act as a P40 Atlassian Code Design interviewer. Choose one family at random: Agent Rating, Middleware Router, API Rate Limiter or Snake Game. Present it as an existing repository extension, not a blank-sheet problem. Require me to clarify semantics, inspect the repository, drive RED-GREEN-REFACTOR with bounded AI prompts, and explain one concurrency or scaling follow-up. Ask one question at a time.

Review the diff

Act as a skeptical senior reviewer. Inspect only the current diff for correctness, placement, security, compatibility, races, error handling, test adequacy and unrelated changes. Give a concrete failure scenario for every concern. Do not edit.

System-design simulation

Strict 60-minute mock

Act as an Atlassian full-stack system-design interviewer. Give me one collaboration-product problem. Let me clarify scope, then introduce scale, permissions, real-time, failure and migration constraints progressively. Evaluate frontend/backend coherence, customer impact, trade-offs and communication. Ask one question at a time and reveal no reference design until the end.

Find hand-waving

Find every place where I named a technology or pattern without defining its key, contract, guarantee, failure behavior or trade-off. Turn each vague statement into the interviewer question I must answer.

Frontend/backend coherence

Audit the connection between my frontend and backend. For each client behavior—optimistic update, pagination, real-time, offline and caching—state the backend contract it requires and flag missing idempotency, ordering, rollback, versioning or permission handling.

Management interview prompts

Project ownership mock

Act as an Atlassian engineering manager. Ask me to walk through one project end to end. Interrupt with one follow-up at a time on business justification, personal ownership, alternatives, technical judgment, collaboration, launch, measurable impact, failure and what I would do differently. Do not accept vague “we” statements. At the end, score scope, specificity, judgment, influence and learning.

Story fact-check

Audit this management answer. Separate confirmed facts, reasonable inferences, missing evidence and claims that sound invented. Identify where I need an exact metric, stakeholder, decision, trade-off or result. Do not rewrite until the truth gaps are listed.

Level and scope calibration

Review this project story for a senior full-stack role. Identify whether it demonstrates ownership across the software lifecycle, cross-team influence, business/customer impact and durable improvement. Ask the five follow-ups most likely to expose overstated scope or weak ownership.

Conflict pressure test

Interview me on this conflict story. Require me to explain the other person's reasonable perspective, what I actually said, how the decision was made, whether I changed my own view, and how trust was preserved. Flag blame, false consensus and a conflict that is really only ambiguity.

Convert technical work into manager language

Using only the facts I provide, turn this project into a STAR-L outline for a management interview. Start with customer/business need, separate my work from team work, include one technical and one people trade-off, use only verified impact, and end with a concrete learning. Mark every missing fact instead of inventing it.

Values interview prompts

One-value mock

Act as an Atlassian values interviewer. Select one of the five values without naming it first. Ask one behavioral question and probe the real tension, the other person's perspective, what I actually said or did, what I sacrificed, the outcome and the behavior I changed afterward. Flag slogans and answers that are mostly technical.

Five-value round

Run a 45-minute Atlassian values mock with one question per value and concise follow-ups. Limit my initial answer to 90 seconds. Probe directness with care, urgency with judgment, customer evidence, team-first behavior and durable change. Give feedback only after all five questions.

Map stories to values

Map these real stories to Atlassian's five values. For each story, state the strongest value, secondary value, genuine tension, observable behavior, verified result, likely follow-ups and missing facts. Do not force a value where the behavior is absent.

Remove rehearsed language

Rewrite this behavioral answer to sound natural and controlled rather than memorized. Preserve every fact. Keep a 90-second core, use simple spoken language, reduce background, make my actions observable, and mark any claim that cannot be supported.

Values red-team

Red-team this values answer. Check for hero narrative, blaming, a trivial trade-off, unsupported customer claims, no personal cost, technical detail crowding out behavior, weak result, missing learning and inconsistency with other stories. Ask one adversarial follow-up for each real weakness.

Story refinement assistant

Interview me for missing facts

Help me complete a behavioral story without inventing anything. Ask one question at a time for situation, stakeholders and their perspectives, my responsibility, exact words/actions, alternatives, verified result, learning and confidentiality boundary. When facts are insufficient, say so and leave a placeholder.

Create 30-second, 90-second and 3-minute versions

Using only this verified story, create three spoken versions: 30 seconds for context, 90 seconds for the default answer and 3 minutes for a deep follow-up. Keep all versions factually identical. In the longer version add tension, stakeholder perspective, evidence and reflection—not new facts.
