Product-agnostic tagging across Jira, Confluence and Bitbucket

Build one tagging platform that can attach tags to different product content, retrieve content by tag, calculate popular tags, respect tenant permissions, and onboard future products without redesigning the core.

Why this is your first system-design practice

This question has appeared repeatedly in public Atlassian candidate reports, including around your experience level. It tests API/data design, extensibility, permissions, search, streaming popularity and the ability to connect frontend experience to backend guarantees.

Interviewer question

Interviewer
Atlassian products contain different content types—for example Jira issues, Confluence pages and Bitbucket pull requests. Design a product-agnostic system that lets users add, remove and update tags, open a tag to see associated content, and view popular tags. New products should be easy to add.

What should I identify first?

Think
  1. The cross-product identity problem: one association must reference content without Jira-, Confluence- or Bitbucket-specific columns.
  2. The permission problem: a tag index must never reveal content a user cannot currently access.
  3. The two read patterns: tags on one item, and content associated with one tag.
  4. The derived view: popular tags should not scan all associations on every request.
  5. The consistency split: tag mutations need durable correctness; search/typeahead/popularity can usually be briefly stale.
The core difficulty is not storing a label. It is defining a stable cross-product content reference, enforcing tenant and content permissions, supporting both association directions efficiently, and maintaining derived search/popularity views without coupling the core service to each product.

Requirements

Functional requirements

  • Create or reuse a tenant-scoped tag and associate it with supported product content.
  • Remove a tag association and rename a tag with optimistic concurrency.
  • List tags attached to a content item.
  • Open a tag and page through authorized associated content across products.
  • Search/type ahead tag names.
  • Show popular tags for a tenant and time window.
  • Onboard a new product through a common content/permission contract.
  • Audit tag and association mutations.

Non-functional requirements

  • Correctness: association create/delete is durable and idempotent.
  • Security: strict tenant isolation and permission-aware results.
  • Latency: mutation p95 under 300 ms; common reads under 200 ms excluding slow downstream permission systems.
  • Availability: core tagging remains available when popularity/search consumers are delayed.
  • Extensibility: new products implement an adapter/event contract rather than change the tag schema.
  • Operability: per-tenant metrics, audit trail, replayable events and safe schema evolution.

Out of scope for the first pass

Automatic AI tag recommendations, complex taxonomy inheritance, cross-tenant public tags and full document search. State these exclusions so the discussion can go deep on the core.

Build the design progressively

Step 1: Make the basic workflow correct

Start with the web client, a Tag API/service and a relational primary store. A normalized content reference avoids product-specific foreign-key columns.

Version 1 · Correct core
flowchart LR
  U[User] --> UI[Product UI / shared tag picker]
  UI --> API[Tag API]
  API --> TS[Tag Service]
  TS --> DB[(PostgreSQL: tags + associations)]
This supports durable create/delete/list operations, but permissions, search and popular tags are not complete yet.

Step 2: Add permission-safe cross-product access

The Tag Service knows only a generic ContentReference. Product adapters or a common permission service resolve metadata and authorize the requesting user. The tag database must not be treated as proof of content access.

{
  "tenantId": "tenant-42",
  "productType": "JIRA_ISSUE",
  "contentId": "ISSUE-8f4a..."
}

Step 3: Derive search and popularity asynchronously

A mutation must not succeed in the database and disappear before an event is published. Store an outbox row in the same transaction, then publish it to a durable stream. Independent consumers update search/typeahead, popularity, audit and cleanup projections.

Step 4: Add cache and partitioning only where load demands it

Cache tag metadata, popular-tag lists and optionally authorized result pages with careful keys and short TTLs. Partition the primary data by tenant (and potentially hashed content/tag within very large tenants) when a single database cluster is no longer sufficient.

Data model

Relational schema

CREATE TABLE tag (
    tenant_id         UUID        NOT NULL,
    tag_id            UUID        NOT NULL,
    normalized_name   VARCHAR(100) NOT NULL,
    display_name      VARCHAR(100) NOT NULL,
    version           BIGINT      NOT NULL DEFAULT 0,
    created_by        UUID        NOT NULL,
    created_at        TIMESTAMPTZ NOT NULL,
    updated_at        TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (tenant_id, tag_id),
    UNIQUE (tenant_id, normalized_name)
);

CREATE TABLE tag_association (
    tenant_id       UUID         NOT NULL,
    tag_id          UUID         NOT NULL,
    product_type    VARCHAR(40)  NOT NULL,
    content_id      VARCHAR(160) NOT NULL,
    created_by      UUID         NOT NULL,
    created_at      TIMESTAMPTZ  NOT NULL,
    PRIMARY KEY (tenant_id, tag_id, product_type, content_id),
    FOREIGN KEY (tenant_id, tag_id)
      REFERENCES tag (tenant_id, tag_id)
);

-- Reverse lookup: tags attached to one content item.
CREATE INDEX idx_association_by_content
ON tag_association (tenant_id, product_type, content_id, tag_id);

-- Stable page through a high-cardinality tag.
CREATE INDEX idx_association_by_tag_created
ON tag_association (tenant_id, tag_id, created_at DESC,
                    product_type, content_id);

CREATE TABLE tag_outbox (
    event_id        UUID PRIMARY KEY,
    tenant_id       UUID NOT NULL,
    aggregate_type  VARCHAR(30) NOT NULL,
    aggregate_id    UUID NOT NULL,
    event_type      VARCHAR(60) NOT NULL,
    payload         JSONB NOT NULL,
    occurred_at     TIMESTAMPTZ NOT NULL,
    published_at    TIMESTAMPTZ NULL
);

Why relational first?

Tag identity and association uniqueness need straightforward constraints and transactions, while the primary access patterns are well known. PostgreSQL is a strong first choice. At much larger scale, shard by tenant or move the association projection to a wide-column/key-value store—but retain explicit uniqueness/idempotency semantics rather than choosing NoSQL generically.

Cursor design

For content-by-tag results, the cursor can encode the last (created_at, product_type, content_id). This yields stable keyset pagination and avoids increasingly expensive offsets.

{
  "createdAt": "2026-10-03T08:31:02Z",
  "productType": "CONFLUENCE_PAGE",
  "contentId": "page-123"
}

A unique association key and idempotency record make client retries safe. Consumers still deduplicate because the stream is at least once.

Read path: content by tag

  1. Validate tenant context and that the user can see the tag itself.
  2. Fetch candidate content references from the association store or search index using a cursor.
  3. Batch-resolve metadata and permissions through product adapters/common services.
  4. Drop inaccessible/deleted items and fetch additional candidates until the page is filled or a scan limit is reached.
  5. Return a mixed product result with a continuation cursor and optional partial-degradation metadata.
Permission-filtering trade-off

Filtering after candidate retrieval is correct but can underfill pages and add latency. Embedding permission principals in the search index can be faster but risks stale access after revocation. A strong answer presents the trade-off and chooses based on permission complexity/freshness requirements.

Frontend architecture

Shared tag picker

  • Debounce suggestions and cancel stale network requests.
  • Separate local input/open state from server state such as suggestions and current tags.
  • Use stable normalized-name duplicate detection, while preserving display casing.
  • Add/remove chips optimistically with a client operation ID; reconcile the authoritative response.
  • Rollback and announce validation/permission failures accessibly.
  • Support keyboard navigation, focus management and screen-reader labels.
  • Do not cache one tenant’s suggestions under another tenant’s key.

Optimistic add flow

  1. Generate operationId; add a chip in pending state.
  2. Submit request with idempotency key.
  3. On success, replace pending representation with authoritative tag ID/version.
  4. On validation conflict, reuse the existing tag returned or refetch.
  5. On permission/server failure, remove the chip and show an actionable message.
  6. If a real-time echo arrives, correlate by operation/event ID to avoid a duplicate chip.

Search and indexing

Tag name typeahead can use a normalized prefix index in PostgreSQL initially. A dedicated search index becomes valuable for fuzzy search, aliases, large scale and mixed content result ranking.

  • Index documents are tenant-scoped and versioned.
  • Consumers use event ID for deduplication and aggregate version to reject stale out-of-order updates.
  • Expose asOf or accept brief staleness for popular/search views.
  • Deletion and permission-revocation events receive high priority.
  • Run reconciliation jobs comparing primary data and index projections.

Popular tags

Define the metric before the technology

A simple all-time association count may favour old tags permanently. A more useful tenant dashboard can score recent events:

score = 3 × tag_association_adds
      + 1 × content_by_tag_clicks
      + 0.5 × searches
      with time decay or fixed windows

Keep weights configurable and version the scoring model so results can be recomputed.

Processing design

  1. Tag and click events enter the durable stream with eventId, tenant, tag, actor and timestamp.
  2. A stream processor deduplicates and updates windowed per-tenant/tag aggregates.
  3. Materialize top tags in Redis sorted sets or a Top-K table keyed by tenant/window.
  4. Serve the dashboard from the materialized result with an asOf timestamp.
  5. Periodically recompute from durable events/aggregates to repair drift and scoring changes.

Security, tenancy and lifecycle

  • Derive tenant from authenticated context; do not trust a free-form tenant ID in the body.
  • Include tenant in every primary key, unique constraint, cache key, event and trace.
  • Authorize mutation against the underlying content and user capability.
  • Authorize content-by-tag results at query time; index membership is not permission proof.
  • Audit actor, content reference, before/after tag and operation ID without sensitive payloads.
  • Process content deletion, tenant deletion and permission changes with tombstones/reconciliation.
  • Rate-limit suggestion/create endpoints and cap tag name/association counts.
  • Escape displayed tag names and handle Unicode normalization consistently.

Scaling plan

  1. Stateless API: horizontal autoscaling behind the gateway.
  2. Tenant-aware database: begin with relational partitioning; assign large tenants to dedicated shards if necessary.
  3. Hot tag mitigation: cursor reads, cached metadata, read replicas and optional hash buckets for extremely high-cardinality projections.
  4. Popularity hot keys: local/windowed partial aggregates combined downstream rather than one global counter write.
  5. Batch permissions: resolve 50–100 candidate references per product call rather than one network call per result.
  6. Bounded fan-out: group candidates by product and apply timeouts/circuit breakers.
  7. Backpressure: monitor consumer lag, throttle non-critical analytics and retain replayable events.
  8. Noisy-neighbour controls: per-tenant quotas, rate limits and metrics.

Interviewer follow-ups

How do you add a fourth product without changing the Tag Service?

The product implements the common adapter contract for batch permission checks, metadata lookup and lifecycle events, and registers a new productType. The association schema already stores a generic content reference. Version the contract and use capability discovery if products support different features.

How do you prevent two users creating “Bug” and “bug” concurrently?

Normalize consistently and enforce UNIQUE(tenant_id, normalized_name). Both requests may race; one insert succeeds, the other handles the unique conflict by loading and returning the existing tag. An idempotency key handles retries from the same operation.

How do you calculate Top-K popular tags?

Emit association/search/click events, deduplicate, aggregate by tenant/tag/window in a stream processor and maintain a Redis sorted set or materialized Top-K table. Periodically recompute from durable aggregates/events so model changes and missed updates can be repaired.

Kafka, SQS or RabbitMQ?

I choose from the requirement. A replayable ordered event log with multiple independent consumers and stream processing favours Kafka-like infrastructure. A managed work queue with simple competing consumers may favour SQS. Complex routing/acknowledgement patterns can favour RabbitMQ. The design needs durability, at-least-once handling and replay for projections; product platform standards also matter.

PostgreSQL, Cassandra or DynamoDB?

PostgreSQL first for tag uniqueness, transactions and known indexes. A key-value/wide-column projection can serve massive content-by-tag/tag-by-content access if scale demands it, with carefully designed partition and sort keys. I would not give up correctness constraints without an explicit scaling reason.

What if one tag is attached to 100 million items?

Never load/count synchronously. Use keyset pagination, precomputed count, cached metadata and read partitioning. If one partition becomes hot, bucket associations by a deterministic hash and merge page candidates, accepting additional query complexity. Search/index projections can shoulder ranked browsing.

How do you handle a permission revocation after results were cached?

Do not rely on a long-lived user-result cache. Re-authorize before returning content, use short-lived/versioned permission caches, consume revocation events for fast invalidation, and fail closed if the authoritative permission dependency is unavailable. Cache metadata separately from access decisions where possible.

How do you rename or merge tags?

Rename uses expected version and the normalized-name uniqueness constraint. Merge is a separate workflow: create/identify target, migrate associations idempotently in batches, emit mapping/tombstone events, redirect old tag during transition, then retire it. Avoid one giant transaction.

What if the event is published twice?

At-least-once delivery is expected. Consumers track eventId or use idempotent upserts and version checks. Popularity updates must not blindly increment twice; deduplicate before applying or aggregate from a unique event log.

What happens if the database commits but the API times out?

The client retries with the same idempotency key. The service returns the stored result instead of creating a duplicate. The unique association constraint is a final safeguard. The client can also refetch authoritative tags after an ambiguous timeout.

How would you support bulk tagging?

Define atomicity explicitly. For large batches, accept a job with an idempotency key, validate permissions in batches, process chunks, expose per-item status and make retries safe. Avoid one transaction across products or thousands of rows.

How would you observe this system?

Track mutation/read latency and error rate by tenant/product, permission dependency latency, unique-conflict rate, idempotency hits, database hot partitions, cache hit rate, outbox age, stream consumer lag, index freshness, dangling-reference rate and popularity snapshot age. Trace operation/event IDs across sync and async paths.

How would you roll out a schema or event change?

Use additive database migration, dual-read/write only when necessary, versioned events with tolerant consumers, canary by tenant, projection backfill and rollback that does not require old consumers to understand new mandatory fields. Monitor lag/error before expanding.

What to draw in the interview

  1. Write the three workflows and permission/freshness assumptions.
  2. Draw Browser → Gateway → Tag Service → PostgreSQL.
  3. Add the generic ContentReference and Product/Permission Gateway.
  4. Add Outbox → Event Stream only when popular/search requirements are discussed.
  5. Add Search and Top-K projections; label them eventually consistent.
  6. Draw one write sequence and one permission-aware read sequence.
  7. Mark tenant boundary, idempotency and the first partition key.

90-second final summary

I designed a tenant-scoped Tag Service around a generic content reference, so Jira, Confluence, Bitbucket and future products do not create product-specific columns. PostgreSQL is the authoritative store for normalized tag identity and unique associations. Every mutation authorizes against the underlying content, writes the association and an outbox event atomically, and returns the authoritative representation for optimistic client reconciliation. A durable stream updates typeahead/search, audit and a windowed Top-K popularity projection; those views may be briefly stale without blocking core writes. Content-by-tag reads fetch candidates with cursor pagination and batch-authorize them before returning results. I would scale APIs horizontally, shard by tenant, mitigate hot tags and enforce per-tenant quotas. The main trade-off is current permission correctness versus the latency of permission filtering; I chose correctness and batch/caching optimizations rather than trusting a stale index.
