About the round title

Atlassian’s public guide describes a 60-minute system-design discussion, while candidate reports for full-stack roles also probe browser-to-database flows, authentication, frontend state and real-time behaviour. Because your recruiter called this “Full Stack Based System Design,” this playbook prepares for the combined signal. The exact balance can vary by interviewer.

P40 research conclusion

The current detailed set remains valid, but the priority is now calibrated to public P40 reports: product-agnostic tagging is the clearest repeated P40 HLD; Confluence most-engaged content is an exact P40 offer-round variant with per-user exclusions; and the Jira/Trello board remains the strongest role-specific full-stack transfer question. For P40, drive APIs, schema, indexes, practical technology choices, concurrency and one or two failure modes without forcing staff-level multi-region complexity into every answer.

The answer framework

User and scopePrimary actor, top workflows, explicit out-of-scope items.
Quality constraintsLatency, availability, freshness, durability, multi-tenancy, permissions and cost.
Core entities and access patternsWhat is stored; dominant reads and writes; ordering and consistency requirements.
API and interaction contractRequests, responses, pagination, idempotency, versioning and real-time channel.
Simple end-to-end designBrowser → API → service → primary store. Prove the basic workflow first.
Evolve for the hard requirementAdd cache, search, events, queues or sockets only when a requirement creates the need.
Failure, scale and securityRetries, duplicates, concurrency, permission changes, hot tenants and observability.
Trade-offs and summaryState what is strongly consistent, eventually consistent, the first bottleneck and deliberate omissions.

A 60-minute pacing guide

0–5 min

Clarify the product

Users, three workflows, scope, real-time/offline needs, tenancy and permissions.

5–10 min

Requirements and scale

Functional/non-functional requirements and only the estimates that change a decision.

10–16 min

Entities and access patterns

Data model sketch, dominant reads/writes and consistency boundaries.

16–23 min

APIs and client contract

Core endpoints/events, cursor pagination, idempotency and concurrency token.

23–36 min

High-level architecture

Simple synchronous path first; then derive async/search/realtime components.

36–48 min

Full-stack deep dive

Frontend state/UX plus database, indexing, cache, queue and consistency.

48–56 min

Failures and scaling

Database, cache, consumer, socket, permission and hot-partition scenarios.

56–60 min

Close

Key guarantees, trade-offs, first bottleneck, rollout and remaining risks.

What to ask before drawing

Ask
  • Who is the primary user, and what are the top three workflows?
  • Is this multi-tenant? Are tenants, projects or workspaces isolation boundaries?
  • Which operations must be real time? Is offline support required?
  • What permission model is in scope, and can access change frequently?
  • What scale, peak traffic and freshness should I assume?
  • Which data must be strongly consistent, and where is brief staleness acceptable?
  • Do we support web only, or multiple clients and public integrations?
  • What can I leave out so we can go deep on the core problem?
I’ll first confirm the core user journeys and quality constraints. Then I’ll define the entities, access patterns and client contract, draw the simplest end-to-end path, and progressively add the components required for permissions, scale, search or real-time behaviour. I’ll keep frontend and backend decisions connected and reserve time for failures and trade-offs.

Delete any box that cannot be justified by a requirement. The strongest design is not the one with the most components.

Full-stack coherence checks

Frontend statementBackend obligation it creates
“The UI updates optimistically.”Idempotency, operation ID, authoritative response, rollback/reconciliation and conflict policy.
“Other users see updates instantly.”Event publication, connection routing, authorization at subscription/delivery, reconnect/catch-up.
“The page supports infinite scroll.”Stable ordering and cursor pagination, not shifting offset pages.
“The app works offline.”Local durable queue, client-generated IDs, retry/deduplication and conflict resolution.
“Search results are cached.”Permission-aware keying, invalidation/revalidation and safe behaviour after access revocation.
“Large lists render smoothly.”Page/chunk API, virtualization-friendly stable IDs and bounded payloads.

Strong P40 signalWhat to demonstrateWhat to avoid
Scope and structureClarify users and core workflows, then drive a coherent simple design.Waiting for the interviewer to choose every component.
API and data modelConcrete endpoints, request/response shape, tables/keys and indexes tied to access patterns.One box labelled backend or naming databases without a schema reason.
Practical technology choicesExplain REST vs GraphQL, Postgres vs Cassandra/DynamoDB, Kafka vs SQS/RabbitMQ in the context of the prompt.Generic claims such as NoSQL scales or Kafka is real time.
Full-stack connectionShow how optimistic UI, pagination, real-time updates and error states create backend obligations.Designing only services and databases for a Full-Stack role.
ReliabilityCover retries, duplicates, permission changes, one hot-key or database failure scenario.Adding active-active multi-region, five queues and CRDTs before the basic workflow is correct.
CommunicationMake assumptions explicit and connect one design choice to your production experience.Reciting a memorized architecture without customer or operational reasoning.

Common weak patterns

  • Starting with React, Kafka, Redis and PostgreSQL before defining the user journey.
  • Drawing only backend boxes and calling the browser “the frontend.”
  • Adding WebSockets without explaining authentication, reconnection and missed-event recovery.
  • Claiming optimistic UI without rollback, idempotency or conflict handling.
  • Using offset pagination on a frequently changing feed or board.
  • Caching permission-sensitive data without discussing revocation and tenant-aware keys.
  • Choosing NoSQL merely because “it scales,” without access patterns or partition key.
  • Claiming exactly-once delivery across services instead of designing idempotent effects.
  • Ignoring audit history, data deletion and API/event compatibility in enterprise collaboration products.
  • Ending without stating guarantees, bottlenecks and unresolved trade-offs.

A strong closing template

The synchronous path guarantees [core invariant] in the primary store. The client uses [state model] and [optimistic or pessimistic behaviour], then reconciles against the authoritative response. Search, analytics and notifications consume durable events and may be stale for [bounded period]. Permission checks are enforced on every authoritative read/write and again before sensitive results are returned. The first scaling boundary is [component/key], which I would partition by [choice]. The main trade-off is [decision versus alternative].
