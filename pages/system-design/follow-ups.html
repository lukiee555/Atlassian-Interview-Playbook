1. Permissions and tenant safety

How would you design permissions?

What is tested: whether security is a first-class part of every path rather than a box beside the API.

Strong answer: define resources and capabilities, derive tenant/user from authenticated context, enforce authorization on authoritative reads and writes, and batch permission checks for list results. Caches and indexes can accelerate candidate lookup but cannot become the only proof of access. Include audit and field/event filtering where users have partial visibility.

What happens when access is revoked while data is cached?

Emit a high-priority revocation event for fast invalidation, keep permission caches short-lived/versioned and re-authorize before returning sensitive results. Do not cache long-lived personalized responses without a permission version. If the permission service is unavailable, fail closed or return fewer results rather than expose stale access.

How do you isolate tenants?

Put tenant context in every key, unique constraint, cache key, event, trace and partition decision. Derive it from authentication rather than trusting request input. Add per-tenant rate limits/quotas and metrics. At larger scale, map tenants to shards and isolate exceptionally large tenants.

How would you prevent one tenant from affecting others?

Use quotas, weighted fairness, per-tenant concurrency limits, partition-aware autoscaling, circuit breakers and isolated queues/partitions for heavy tenants. Monitor latency and resource use by tenant so global averages do not hide noisy neighbours.

2. Duplicate events, retries and idempotency

How do you handle duplicate events?

Assume at-least-once delivery. Give every event a stable ID, make the consumer effect idempotent and track applied IDs or enforce a unique application key. For counters, blind increments are unsafe; deduplicate first or derive counts from a unique normalized event log.

What if the API times out after the database commit?

The client retries with the same idempotency key. The service stores or derives the original result and returns it instead of repeating the effect. A domain unique constraint is the final safety boundary. The UI may refetch authoritative state after an ambiguous timeout.

Can you guarantee exactly-once processing?

Not end to end across independent systems in the general case. I design at-least-once delivery with idempotent effects, transactions where the boundary is local, and an outbox/inbox or deduplication mechanism. “Effectively once” describes the resulting business effect, not magical transport semantics.

What is the transactional outbox solving?

It prevents the dual-write gap where database state commits but event publication fails—or the event publishes before the state commits. The domain change and outbox row are one database transaction; a separate publisher retries. The cost is duplicate delivery and outbox operations, so consumers remain idempotent.

How do you handle poison messages?

Classify retryable versus permanent failures, use bounded retries with backoff, send irrecoverable events to a dead-letter/quarantine stream with context, alert and provide replay after correction. Do not block the entire partition forever without an operational policy.

3. Concurrent updates

How do you handle two users updating the same item?

Choose a product policy first. For edits where silent overwrite is harmful, include entity version/ETag and use optimistic concurrency: one succeeds; stale writes receive 409 and authoritative state. The client merges, retries or asks the user. Last-write-wins is acceptable only when explicitly chosen.

Optimistic or pessimistic locking?

Optimistic locking fits user-facing systems where conflicts are relatively rare and holding locks across think time is impossible. Pessimistic locks fit short, high-contention critical sections. State the contention profile and lock scope rather than choosing by habit.

How do you resolve collaborative text edits?

Start with the required granularity. Version checks or block-level conflict handling may be enough. Character-level simultaneous editing can justify operational transformation or CRDTs, which add significant complexity around operations, metadata, compaction and permissions. Do not introduce them without the collaboration requirement.

How do you maintain ordering under concurrent inserts?

Use a sortable rank/sequence owned by the server, generate between neighbouring items under concurrency control, include a deterministic tie-breaker and rebalance bounded ranges when needed. For event streams, partition by the entity boundary that needs order, such as board or conversation—not globally.

4. Real-time updates and reconnects

How would you support real-time updates?

Commit authoritative state first, publish an outbox event, deliver through a realtime gateway and include event ID, entity version and sequence. Authenticate/authorize subscriptions, deduplicate at clients, apply only newer versions and provide reconnect recovery. State whether SSE or WebSockets better matches the directionality.

WebSockets, SSE or polling?

Polling is simplest for low-frequency/non-urgent changes. SSE provides server-to-client streaming over HTTP with straightforward reconnection. WebSockets support bidirectional, low-latency interactions but add connection lifecycle, routing and backpressure complexity. Choose from behaviour and existing infrastructure.

What happens when the client disconnects?

Persist the last sequence/cursor, reconnect with exponential backoff and jitter, and request events after that sequence. If the gap is too old or large, send a resync-required response and fetch a current snapshot. Pending client mutations retain operation IDs for safe retry.

How do you handle slow clients?

Bound per-connection buffers, collapse superseded state updates, apply backpressure and eventually send a resync marker/close the connection rather than consume unbounded memory. Presence/cosmetic updates can be dropped more aggressively than durable domain events.

How do you revoke a realtime subscription?

Authorize on connection/subscription, consume permission-change events and close or downgrade affected subscriptions. Every mutation/read still checks authority because the socket’s original permission may be stale.

5. Database and storage failures

What happens if the database goes down?

Do not acknowledge writes. Use bounded retries only for safe/idempotent operations, fail over according to the database topology and surface a clear temporary failure. Reads may use a bounded stale cache only when the product and permission model allow it. Protect the recovering database from a retry storm.

How do you choose SQL versus NoSQL?

Start with invariants and access patterns. SQL is strong for transactions, uniqueness, joins and flexible query evolution. Key-value/wide-column stores fit known partition/sort-key access and very large horizontal scale. Document stores fit aggregate-shaped data. State partition key, consistency and secondary-index limits—not “NoSQL scales.”

How do you shard the database?

Choose a key that aligns with isolation and common transactions—often tenant, then entity/board for very large tenants. Maintain a shard directory, avoid cross-shard transactions, plan resharding and prevent hot tenants from dominating one shard. Sharding is a later scaling step, not the first diagram.

What about replication lag?

Route reads requiring read-after-write or current permissions to the primary or use a consistency token. Eventually consistent list/search reads can use replicas. Explain what stale data the customer can see and how the client reconciles.

How do you perform schema migration safely?

Use expand-and-contract: add compatible fields/tables, deploy code that supports old/new, backfill gradually, switch reads, then remove old structures. Track progress, throttle impact, canary and make rollback possible without losing newly written data.

6. Scaling to millions of users

How would you scale this to millions of users?

First identify the bottleneck from reads, writes, connections, storage or one hot key. Scale stateless APIs horizontally, cache safe hot reads, move secondary work async, partition data/events by an access-aligned key, batch downstream calls and enforce per-tenant quotas. Give a sequence, not a bag of technologies.

What is a hot partition and how do you fix it?

A disproportionate key routes too much load to one shard/consumer. Mitigate through a better/salted partition key, local partial aggregation, dedicated capacity for hot tenants/entities, caching and product limits. Salting complicates ordered reads/aggregation, so state that trade-off.

How do you handle a celebrity board/tag/page?

Separate read fan-out from the authoritative write boundary. Cache/materialize reads, isolate its event partition, combine counters hierarchically and use hierarchical pub/sub. Keep writes ordered only where necessary and monitor the entity independently.

How do you reduce downstream fan-out?

Batch by product/service, cache stable metadata, denormalize safe projection fields, apply deadlines and cap candidate scans. Avoid one network call per list item. A BFF/query service can orchestrate but should not become an unbounded serial bottleneck.

What would you rate limit?

Protect expensive mutation/search endpoints, abusive event producers and per-tenant resources. Use actor, tenant, token and sometimes resource keys. Return retry guidance and avoid a limiter that allows one tenant to exhaust shared capacity.

7. Caching and latency

What would you cache?

Cache data that is expensive, frequently read and safe to be stale: metadata, configuration, popular snapshots and search suggestions. Be cautious with user-specific permission-sensitive results. Name the key, TTL, invalidation trigger, source of truth and behaviour on cache miss/failure.

How do you invalidate the cache?

Use versioned keys or explicit update/delete events for critical changes, plus TTL as a safety net. For writes, update/invalidate after the authoritative commit. Permission revocations get priority. Accept that perfect distributed invalidation is hard and design safe staleness bounds.

How would you improve latency?

Measure the path first. Common levers are batching, indexes, keyset pagination, cache, smaller payloads, parallel independent calls, edge delivery, connection reuse and moving secondary work async. State which percentile and dependency dominate rather than saying “add Redis.”

Why cursor pagination instead of offset?

Keyset/cursor pagination uses an indexed sort key, remains efficient for deep pages and is more stable under concurrent inserts/deletes. Offset is simple for small/static data but can skip/duplicate items and becomes expensive at large offsets.

How do you cache a changing feed?

Materialize/version snapshots and tie cursors to the snapshot. Cache candidate lists separately from user permission filtering. Signal that a new snapshot exists instead of silently mixing orders during pagination.

8. Failures, observability and rollout

How would you handle failures?

Classify the component as authoritative or derived. Define timeout, retryability, idempotency, circuit-breaker/fallback, user-visible degradation, backlog/replay and alert. Preserve core invariants; degrade search, popularity or realtime before compromising correctness/security.

What would you monitor?

Golden signals—latency, traffic, errors, saturation—plus domain signals: conflict/rollback, permission rejection, idempotency hits, outbox age, consumer lag, index freshness, cache hit, hot tenants, stale snapshot age and customer-visible completion. Trace operation/event IDs across async paths.

How would you roll out safely?

Backward-compatible contracts, feature flag, dark/shadow reads where useful, canary by tenant, metrics and explicit rollback. For projections, dual-build and compare before switching. For data changes, use expand-and-contract.

How do you recover from a bad event consumer?

Stop or isolate it, preserve the durable stream, roll back code/config, reset projection state from a known checkpoint/snapshot and replay idempotently. Version outputs so bad older writes cannot overwrite corrected state.

What is graceful degradation here?

Keep the core action correct while optional experiences become stale or unavailable. Example: tag writes work while popular tags are hidden; board moves work while collaborator realtime falls back to refresh. Tell the user when freshness is reduced.

Rapid two-minute drill

For each prompt below, answer aloud using the six-part pattern:

  • The permission service is taking three seconds.
  • A Kafka consumer applied every popularity event twice.
  • One board has 500,000 cards and 20,000 concurrent viewers.
  • A WebSocket reconnect misses ten minutes of changes.
  • The database commits a card move but the API response is lost.
  • A tag rename is visible in PostgreSQL but not search.
  • A page is made private while present in a cached popular feed.
  • A deployment changes the event payload while old clients remain connected.
Practise by answering before expanding each section.
