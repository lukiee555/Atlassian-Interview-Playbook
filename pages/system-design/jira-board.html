P40 detailed playbook 3 - Collaboration + ordering

Jira / Trello-style work board

Design a board where users create cards, drag them across columns, reorder them, collaborate in real time and preserve workflow rules, permissions and activity history.

Candidate-reported full-stack topicP40 calibratedOptimistic UIOrderingRealtime
On this page
Why this stays in the P40 set

Tagging and the Confluence engagement homepage have stronger direct P40 report evidence, but the board remains the best Full-Stack transfer drill. It forces you to connect React state, optimistic UX, API contracts, transactional ordering, workflow validation and real-time reconciliation. At P40, go deep on those concrete paths rather than adding staff-level global architecture by default.

The hard part

CRUD is not the differentiator. The design should explain stable ordering without renumbering an entire column, optimistic drag-and-drop with rollback, legal workflow transitions, concurrent collaborators, event ordering and permission revocation.

Interviewer question

Interviewer
“Design a Jira or Trello-style board with tasks, columns/statuses and priorities. Users should be able to move and reorder cards, and collaborators should see changes.”

What should I identify first?

Think
  1. The board is an ordered view over cards, not necessarily the source of all issue data.
  2. A move changes column/status and order together; that state transition must be atomic.
  3. The UI should feel instant, so optimistic updates need an idempotent/versioned backend contract.
  4. Collaborators require ordered change events plus reconnect/catch-up behaviour.
  5. Workflow and permissions may reject a visually valid drag.
I’ll scope the card model and workflow first, then focus on the two difficult guarantees: stable order within a column and correct reconciliation when multiple users move cards concurrently. I’ll connect the React drag-and-drop state to an idempotent, versioned backend mutation and an ordered real-time event stream.

P40 target depth

  • Define the move-card API precisely: operation ID, expected version, target column and neighboring rank anchors.
  • Propose tables and indexes for loading a column in rank order and updating one card atomically.
  • Explain one ranking strategy and its rebalance trade-off rather than listing many algorithms.
  • Connect the optimistic React update to rollback, authoritative response and echoed realtime event handling.
  • Handle two concurrent moves of the same card with versioning/conflict response.
  • Cover permission/workflow rejection and one reconnect/event-gap scenario.
  • State what you would postpone: offline write conflict resolution, global active-active and arbitrary workflow plugins unless asked.

Requirements

Functional requirements

  • Create/edit/archive cards with title, assignee and priority.
  • Load board columns and page cards in rank order.
  • Move a card within or across columns.
  • Validate workflow transitions and permissions.
  • Show collaborators’ changes in near real time.
  • Filter the board without changing canonical order.
  • Record activity history and support retry-safe mutations.

Non-functional requirements

  • Interactive drag response under 100 ms locally; server confirmation p95 under 400 ms.
  • Durable card transitions and order; no silent duplicate mutation.
  • Ordered events per board, with recovery after connection gaps.
  • Tenant/project isolation and prompt permission revocation.
  • Large-column pagination and frontend virtualization.
  • Graceful degradation when realtime or secondary consumers fail.

Build the design progressively

Step 1: Simple correct board

A React client calls a Board API. The Board Service reads/writes board, column and card rows in PostgreSQL. Start here before adding sockets, cache or events.

Step 2: Solve ordering

Sequential integer positions are easy initially but expensive when inserting near the top because many rows may need renumbering. Use a sortable rank key with space between values—a fractional or LexoRank-style key—and rebalance a bounded column segment only when rank space is exhausted.

Example rank idea

Cards might have keys a0, a5, b0. Inserting between a0 and a5 creates a key in between. The server—not the browser—owns canonical rank generation.

Step 3: Make drag-and-drop optimistic

The client applies the move immediately, saves a rollback snapshot and sends operationId, target neighbours and expectedVersion. The server validates workflow/permission, computes the rank transactionally and returns authoritative card/version/rank.

Step 4: Publish committed board events

Write an outbox event in the same transaction. A publisher delivers ordered events partitioned by board ID. Realtime gateways distribute them to authorized subscribers; clients track a board sequence and refetch if a gap is detected.

Why board sequence matters

A monotonically increasing sequence per board lets clients detect missing events. It does not require global ordering across all boards. Generate it transactionally with the card update, using a board sequence row/counter or database-supported mechanism that does not become a global bottleneck.

Optimistic move algorithm

  1. Cancel drag if the UI already knows the transition is impossible—but still let the backend decide authoritatively.
  2. Capture source/target list snapshots and card version.
  3. Apply local array move immediately and mark the card pending.
  4. Send a unique operation ID and neighbour IDs.
  5. Reconcile server rank/version on success.
  6. On a matching realtime echo, clear pending state instead of applying a duplicate.
  7. On conflict/denial, rollback and refetch only affected columns.

Large-board performance

  • Virtualize cards within long columns and avoid rendering hidden details.
  • Page each column independently with cursor-based rank keys.
  • Lazy-load card detail/attachments after selection.
  • Use normalized entities so one card update does not rerender the entire board.
  • Throttle presence/cursor indicators; do not persist them as card state.
  • Support keyboard drag, focus restoration and screen-reader announcements.

Ordering and rebalancing

A rank scheme must preserve lexical sort and generate a key between neighbours. When there is no representable gap or keys grow too long, schedule a rebalance for a bounded column segment.

Approach
  • Store canonical rank keys in the database and index by column + rank.
  • Generate new keys on the server under concurrency control.
  • Add card ID as a deterministic tie-breaker if two equivalent keys can temporarily occur.
  • Rebalance in the background or transactionally for a small range; version the column so clients can refetch.
  • Do not renumber 100k rows during one user drag.

Concurrency model

RacePolicy
Two users move the same cardOptimistic card version; one succeeds, the stale request returns 409 with authoritative state.
Two cards inserted between same neighboursRank generator + transaction/unique tie-break; retry one computation if conflict.
Card moved while its fields are editedField-level patch or version policy; avoid rejecting independent fields unnecessarily if architecture supports it.
Column deleted during a moveForeign-key/workflow validation fails; rollback client and refresh board metadata.
Workflow changes while board is openVersion workflow config; server rejects invalid transition and broadcasts configuration update.

Realtime design

WebSockets are useful when the same connection may later support presence, comments or bidirectional collaboration. SSE is simpler for server-to-client board events. Choose based on product needs and existing platform—not fashion.

  • Authenticate the connection and authorize board subscription.
  • Partition event stream by board ID to preserve per-board order.
  • Include eventId, operationId, boardSequence, entity version and actor summary.
  • On reconnect, send last known sequence; replay bounded events or request a fresh snapshot if retention/gap is too large.
  • Deduplicate event IDs and ignore stale entity versions.
  • Re-evaluate or terminate subscriptions after permission revocation.
  • Use heartbeat, connection limits and backpressure for slow clients.

Permissions and security

  • Tenant/project/board context comes from authenticated access, not the mutation body.
  • Separate view, create, edit, transition, administer and archive capabilities.
  • Validate field-level/workflow rules server-side.
  • Realtime gateways authorize the initial subscription and respond to revocation events.
  • Activity events avoid leaking hidden fields to users who can view only a subset.
  • Escape rich card text and protect attachment flows independently.
  • Rate-limit mutation bursts and protect expensive filters.

Scaling plan

  1. Partition relational data and event traffic by tenant then board ID; keep one board’s write/order boundary together.
  2. Horizontally scale query/command services and realtime gateways.
  3. Use column-level pagination and read replicas/materialized snapshots for high-read boards.
  4. Cache board metadata/workflow configuration with versioned invalidation; be cautious caching permission-sensitive card pages.
  5. For a “celebrity” board, isolate its stream partition, rate-limit automation and fan out events through a hierarchical pub/sub layer.
  6. Move activity/search/notification work off the transaction path through the outbox.
  7. Apply per-tenant quotas and monitor board size, mutation rate, socket count and consumer lag.

Interviewer follow-ups

Why not store positions as 1, 2, 3…?

Moving a card near the top can require updating many rows, creating write amplification and lock contention. Fractional/lexicographic rank keys usually update only the moved card, with occasional bounded rebalance.

What if two users move the same card at once?

Each request includes the card version. The first committed move increments it; the stale request returns 409 and authoritative state. Its client rolls back/reconciles rather than silently overwriting. Product policy could instead choose last-write-wins, but it should be explicit.

How do clients recover missed WebSocket events?

Track the last board sequence. On reconnect, request events after it. If the gap is outside retention or too large, return a resync marker and fetch current board metadata plus affected column pages.

WebSocket or SSE?

SSE is simple for server-to-client events and automatic HTTP reconnection. WebSockets fit bidirectional presence/collaboration and many event types but add connection routing/backpressure complexity. For board changes alone either works; I would follow platform standards and future interaction needs.

How do you support 100,000 cards in one column?

Keyset paginate by rank, virtualize the UI, lazy-load details and never broadcast full-column snapshots for each change. Use compact move events and fetch neighbours/pages as needed. Consider product limits because a 100k-card kanban is also a UX problem.

What if a workflow transition is rejected after an optimistic drag?

The client restores the snapshot or applies the authoritative response, puts focus back on the card and explains why the move is not allowed. The backend remains authoritative; frontend prechecks reduce but cannot eliminate rejections.

How would you implement undo?

Capture the previous column/neighbour context and submit a new inverse move with the latest expected version. Undo is another auditable mutation, not deletion of history. It can fail if workflow/permissions changed, which the UI must report.

How do you handle custom fields?

Keep core indexed fields typed. Model tenant/project-defined fields through schema metadata and typed values or a document projection, with validation and selected indexes for frequently queried fields. Avoid an unbounded EAV query path for everything without discussing performance.

How do you cache the board?

Cache relatively stable board/column/workflow metadata by version. Card pages are mutable and permission-sensitive; client/server caches can use short TTL/ETag and event invalidation. Avoid one monolithic board blob that must be rewritten for every move.

What metrics would you monitor?

Board load/move latency, conflict and rollback rate, idempotency replay, rank-key length/rebalance frequency, database lock time, outbox age, consumer lag, socket count/reconnect/gap rate, permission rejection, large-board page latency and per-tenant hot keys.

How would you roll out a new move contract?

Add fields compatibly, accept old/new requests during transition, version events, make consumers tolerant, canary clients/tenants and monitor conflicts. Do not require every browser tab to update simultaneously.

90-second final summary

The React board loads column metadata and paged rank-ordered cards, keeps remote data in a normalized server-state cache and applies drag moves optimistically with an operation ID and rollback snapshot. The move API sends target neighbours and expected card version. The Board Service authorizes the user, validates the workflow, computes a server-owned fractional rank and atomically updates column, rank, card version, board sequence and an outbox event in PostgreSQL. Ordered per-board events are delivered through a realtime gateway; clients deduplicate by event/operation ID and recover sequence gaps through replay or snapshot refresh. Search, activity and notifications are asynchronous. I would partition by tenant/board, virtualize large columns and isolate hot boards. The main trade-off is optimistic responsiveness versus reconciliation complexity, which the versioned/idempotent contract handles.
