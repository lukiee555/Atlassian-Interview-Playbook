Confluence most-engaged homepage

Rank the most-engaged documents across an organization, then personalize the result by excluding pages the requesting user authored or already read while preserving current permissions, low latency and a stable frontend experience.

Why this is P40 priority 2

A September 2025 P40 offer report describes a YouTube-like Confluence homepage showing the most engaged documents while excluding documents the user authored or already read. The candidate specifically received database-schema feedback around per-user ranking and read-history filtering. This playbook therefore treats candidate generation plus user-specific exclusion as the central design problem, not an optional personalization extension.

The key interview move

Separate the problem into two stages: build a reusable organization/space Top-K candidate set from engagement events, then overfetch and apply user-specific authored/read exclusions plus current permission checks. Do not create a full ranking per user unless the scale and requirements force it.

Interviewer question

Interviewer
Design a YouTube-like homepage for Confluence that shows the most engaged documents across the organization. For the requesting user, do not show documents they authored or documents they have already read. The result must also respect current content permissions.

What should I think about first?

Think
  1. Define engaged. Views, likes, comments, shares, recency, unique users and scope determine the reusable candidate ranking.
  2. Separate candidates from personalization. Precompute organization/space Top-K, then exclude authored, already-read and unauthorized documents at read time.
  3. Model read history for membership queries. The read path asks whether this user has seen each candidate, not for a full scan of everything the user has read.
  4. Overfetch deliberately. Exclusions can remove many candidates, so fetch Top-M to fill a page of N with a bounded scan.
  5. Keep permissions authoritative. Ranking and read-history projections may be eventually consistent; access control must not leak restricted pages.
  6. Protect UX stability. Fresh rankings should not make the visible list jump continuously.
I will first define engagement, scope, freshness and what counts as already read. Then I will build a reusable Top-K candidate pipeline and a separate request-time filtering path for author, read history and permission. I will overfetch with a bounded candidate scan, keep the client snapshot stable, and discuss when the exclusion data can be eventually consistent versus where we must fail closed.

Requirements

Functional

  • Accept engagement events from supported products/clients.
  • Deduplicate retries and control repeated views.
  • Compute ranked content per tenant/space and time window.
  • Return permission-safe pages while excluding content authored or already read by the requesting user.
  • Overfetch and scan candidates with a bounded limit to fill the requested page.
  • Indicate when fresher rankings are available.
  • Remove deleted/inaccessible content promptly.
  • Support replay and scoring-model changes.

Non-functional

  • High-throughput, durable event ingestion with backpressure.
  • Feed API p95 under 200 ms for cached/materialized ranking.
  • Ranking freshness under one minute.
  • At-least-once delivery tolerated through idempotent/deduplicated processing.
  • Tenant isolation, permission correctness and user-history privacy.
  • Observable lag, event quality, model version and stale-result age.

Popularity model

Start with an explainable score and keep the model versioned/configurable:

rawScore = 1 × uniqueViews
         + 3 × likes
         + 5 × comments
         + 7 × shares

finalScore = rawScore × recencyDecay(age)
             × qualityFactor
             × abuseAdjustment

Examples of scope key: (tenantId, optionalSpaceId, window, modelVersion). Do not hard-code weights into event storage; durable raw or normalized aggregates allow recomputation.

Build the design progressively

Step 1: Durable event collection

Clients or product services send an event with a unique ID. An ingestion API authenticates the producer, validates tenant/content/type and appends to a durable stream quickly. It does not update feed rows synchronously.

Step 2: Windowed aggregates

A stream processor deduplicates, applies event-time windows and keeps per-tenant/content counters. It handles late events within an allowed watermark and writes durable aggregate checkpoints.

Step 3: Materialize reusable Top-K candidates

Maintain a larger candidate snapshot per tenant/space/window/model in Redis sorted sets or a fast key-value store, backed by durable aggregates for rebuild. Do not materialize one ranking per user at this stage.

Step 4: Apply user-specific exclusions

The Feed API fetches a bounded candidate batch, batch-checks user read membership, removes documents whose author is the requester, batch-authorizes the remainder, and continues to the next candidate batch until it fills the page or reaches the scan cap.

Step 5: Freshness without a jumping UI

Publish a lightweight RankingUpdated(scope, snapshotVersion) event. Connected clients show “New popular content available” and refresh at a safe moment rather than automatically reordering the list under the user.

Aggregation and Top-K

Exact first version

For each tenant/window/content, update windowed counters in a stateful stream processor. Periodically score active content and update the tenant/window sorted set. This is understandable and often sufficient.

At extreme scale

Use local partial aggregates per stream partition, then merge them. For very high-cardinality scopes, approximate heavy-hitter algorithms can reduce memory, but the interviewer should hear the error/complexity trade-off and why exact computation is insufficient.

Late events

  • Process event time with a watermark, for example accepting events up to five minutes late in the live window.
  • Events later than the watermark go to a correction path or next periodic recomputation.
  • Snapshot versions ensure an older computation cannot overwrite a newer materialized ranking.

If fewer than 20 survive, fetch the next bounded candidate batch. The cursor tracks the candidate snapshot and scan position so filtering does not create duplicates or an unbounded query.

Read-history data model and access pattern

CREATE TABLE user_content_interaction (
  tenant_id        VARCHAR NOT NULL,
  user_id          VARCHAR NOT NULL,
  content_id       VARCHAR NOT NULL,
  first_read_at    TIMESTAMP NOT NULL,
  last_read_at     TIMESTAMP NOT NULL,
  read_count       BIGINT NOT NULL,
  PRIMARY KEY (tenant_id, user_id, content_id)
);

-- Candidate filtering asks membership for a bounded ID set:
SELECT content_id
FROM user_content_interaction
WHERE tenant_id = :tenantId
  AND user_id = :userId
  AND content_id IN (:candidateIds);

At very large scale this can live in a user-partitioned wide-column/KV store or a compact per-user read projection. The key requirement is efficient candidate membership checks; do not load the user's entire history for every homepage request.

Frontend architecture

State and rendering

  • Keep the loaded snapshot/version stable while the user reads or scrolls.
  • Use cursor pagination tied to snapshot/order where possible.
  • Virtualize long lists and lazy-load heavy previews/images.
  • Cache server state by tenant/user/scope/window/filter; never reuse personalized results across users.
  • Show loading skeleton, empty state, partial-degradation and stale asOf state.
  • Prefetch next page near the viewport, respecting bandwidth.

Realtime update experience

  1. Subscribe to a scope-specific ranking version stream.
  2. When a newer version arrives, set hasNewResults=true; do not reorder immediately.
  3. Show a “12 new popular pages” or “Refresh results” affordance.
  4. On refresh, preserve scroll focus where practical and fetch the new snapshot.
  5. If an item is deleted or access is revoked, remove it immediately rather than waiting for a manual refresh.
Customer-centred trade-off

Technical real time does not require visual real time. A stable list with a freshness indicator is usually less disruptive than continuous rank movement.

User exclusions, permissions and content lifecycle

  • Already-read filtering is a recommendation rule, not an authorization rule; define its acceptable staleness separately.
  • Authored filtering uses authoritative page creator/author metadata and must define behavior after ownership transfer.
  • Ranking candidates are not authorization evidence; batch-check current access before returning metadata.
  • Use deletion/permission-change events to remove candidates quickly, but keep read-time authorization as the safety boundary.
  • Fail closed when permission verification is unavailable; optionally serve fewer items instead of exposing unverified content.
  • Cache permission decisions briefly and version/invalidate them; avoid long-lived personalized full-response caches.
  • Do not let engagement events reveal page existence across tenant or space boundaries.

Scaling and hot partitions

  1. Partition raw events by tenant + hashed content, while preserving state locality needed by aggregation.
  2. Use partial per-partition aggregates, then combine to tenant Top-K; avoid one counter for a viral page.
  3. Give exceptionally large tenants dedicated partitions/processor capacity.
  4. Materialize only Top-N plus buffer, not every sorted score in Redis.
  5. Batch read-membership, permission and metadata calls; avoid loading a user's full history.
  6. Partition read history by tenant + user and protect hot/service-account users with pagination or bucketed partitions.
  7. Separate ranking update notifications from full feed payloads.
  8. Set quotas and backpressure for noisy producers; monitor per-tenant lag.

Observability

  • Event acceptance rate, schema rejection and duplicate ratio by producer.
  • End-to-end event-to-ranking freshness and per-stage consumer lag.
  • Top-K snapshot age, rebuild duration and model version.
  • Feed latency, candidate overfetch ratio, read/authored exclusion rate and permission-filter rate.
  • Missing/deleted metadata rate and revocation-removal latency.
  • Abuse-signal rate and contribution caps.
  • Percentage of returned pages that were actually unread, user-history lag, client refresh acceptance and empty/partial feed rate.

Interviewer follow-ups

How do you filter a user with millions of read documents?

Do not fetch the full history. Fetch a bounded Top-K candidate batch and perform a batch membership query for only those IDs, keyed by tenant and user. If the candidate survival rate is low, fetch the next batch up to a scan cap or use a compact read projection/Bloom filter as a negative prefilter backed by an exact check where needed.

What if nearly every Top-K document has already been read?

Overfetch in bounded pages, then fall back to a broader candidate source such as recent content from followed spaces, team-level trends or newly published documents. Return fewer items rather than running an unbounded scan, and track candidate survival as a product/operational metric.

How do you cache a personalized homepage?

Cache shared Top-K candidates broadly, but key final results by tenant/user/scope/window and keep the TTL short. Often it is better to cache candidate and metadata layers separately, because every read event invalidating a full user response causes churn.

What if the page was just read but the event pipeline is delayed?

The client can optimistically mark the page read in local/server state and send an idempotent read event. A brief repeat recommendation is acceptable if product agrees; expose a bounded freshness target and reconcile the durable interaction projection asynchronously.

How do author changes or page ownership transfers affect exclusion?

Clarify whether the rule means original creator, current owner or any contributor. Store the chosen field in authoritative metadata and version lifecycle changes. Do not infer authorship from engagement events.

How do you compute Top-K without sorting every page?

Incrementally aggregate scores by content/window and maintain a bounded sorted structure/materialized Top-K per scope. At very high cardinality, combine partition-local candidates or use approximate heavy-hitter algorithms, then exact-score the candidate set.

How do you handle duplicate events?

Every event has an ID. The processor maintains bounded dedup state or writes idempotently against a unique event application key. For popularity increments, blindly replaying is unsafe; deduplicate before updating or recompute from a unique normalized log.

What if events arrive out of order or late?

Use event-time windows and watermarks. Accept normal lateness into the active window, route very late events to correction/recomputation, and version snapshots so old output cannot overwrite newer ranking.

How do you prevent one viral page from creating a hot key?

Aggregate locally across stream partitions/shards and merge partial counts rather than writing every event to one remote counter. Salting can spread writes, with a combiner producing the final score.

How do you remove a page immediately after permission revocation?

Publish high-priority lifecycle/permission events to invalidate materialized candidates and caches, but still batch-authorize at read time. If permission verification is unavailable, fail closed rather than trust stale ranking state.

Would you use WebSockets or SSE for feed updates?

The server only needs to signal a new ranking version, so SSE is sufficient and simpler. If the product already has a shared WebSocket channel for bidirectional collaboration, reuse may win. The payload should be a version/freshness signal, not the whole feed.

How would you go beyond authored/read exclusions?

Keep shared tenant/space candidates as retrieval, then re-rank the allowed unread set using followed spaces, team affinity, topics, recency and diversity. Version the model and protect privacy. The exact P40 requirement can be met without a machine-learning recommender.

How do you change scoring weights safely?

Version the model/configuration, shadow-compute new snapshots from durable aggregates/events, compare quality/operational metrics, canary selected tenants and switch a pointer. Retain the previous snapshot/model for rollback.

What if Redis loses all Top-K data?

Redis is a serving projection. Rebuild from durable aggregate snapshots or replay the event log from a checkpoint. During recovery, serve the last durable snapshot with a stale marker or degrade the widget.

How would you paginate a changing ranked feed?

Tie the cursor to a snapshot version and last score/tie-break ID. Continue within that snapshot for stable results. A newer ranking is offered as a refresh rather than silently mixing orders across pages.

How do you protect against gaming?

Deduplicate repeated actions, cap contribution per actor/session, incorporate trust/quality signals, detect anomalies and keep raw/audit evidence. Do not disclose exact score mechanics unnecessarily. Separate product ranking from security enforcement.

What is the first bottleneck?

Likely state skew from very large tenants/viral content or permission enrichment latency—not the Feed API itself. I would measure partition lag, hot keys and candidate-to-return ratio before introducing approximate algorithms or more shards.

90-second final summary

I separated shared candidate generation from per-user filtering. Engagement events are deduplicated and aggregated into versioned tenant/space Top-K candidate snapshots. On read, the Feed API overfetches a bounded candidate batch, batch-checks the requesting user's read history, removes documents they authored, batch-authorizes the remainder, enriches metadata and returns a stable snapshot cursor. This avoids the write amplification of precomputing every user feed while keeping the exact P40 exclusions explicit. Ranking and read history can be briefly eventual, but permission checks remain authoritative. The client does not reorder continuously; it receives a freshness signal and refreshes deliberately. The main trade-off is variable read-time filtering cost versus scalable reusable candidate ranking.
