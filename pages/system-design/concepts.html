Quick concept reference

System-design concepts in interview language

Each concept answers three questions: what it is, when it earns a place in the diagram, and what sentence demonstrates judgment rather than buzzword recall.

On this page

Traffic and service architecture

Load balancing

Distributes requests or connections across healthy instances. It can be layer 4/7 and may need connection-aware routing for WebSockets.

Say: “The service is stateless, so requests can go to any instance; connection state lives in a shared registry or is routed consistently only where needed.”

Horizontal scaling

Add more instances/partitions rather than only making one machine larger. It requires externalized state and partitionable workload.

Use when: traffic or connections exceed one instance; name the remaining shared bottleneck.

API Gateway / BFF

A gateway handles cross-cutting routing/auth/rate limits; a BFF shapes data for a particular client experience.

Trade-off: fewer client round trips versus another orchestration/bottleneck layer.

Rate limiting

Controls requests/events by actor, tenant, token or resource over a window.

Say: “I’ll protect expensive endpoints and shared capacity with tenant-aware limits, return retry guidance and avoid one global key.”

Backend service boundary

A service owns a cohesive business capability and its invariants/data—not simply one table or one endpoint.

Use when: independent scaling/ownership/failure boundaries justify separation; start simpler otherwise.

CDN

Serves cacheable static assets and sometimes public/edge-safe responses close to users.

Do not use for: sensitive dynamic responses without correct cache keys and authorization behaviour.

Data modelling and storage

SQL database

Relational schema with transactions, constraints, joins and secondary indexes.

Choose when: invariants/uniqueness/transactions and evolving queries matter.

NoSQL

Key-value, document or wide-column models optimized around specific access and partition patterns.

Say: the exact partition and sort key, consistency model and unsupported query—not “it scales.”

Database indexing

An ordered/hashed structure that accelerates particular filters/sorts at the cost of storage and write work.

Rule: derive composite index order from equality filters, range and sort; confirm with access patterns.

Partitioning / sharding

Splits data/work among nodes by a key. A poor key creates hotspots or cross-shard operations.

Say: “Tenant/board keeps common transactions local; I need a resharding plan for very large tenants.”

Replication

Copies data for availability/read scale. Replicas may lag and failover may lose the latest asynchronous writes.

Ask: which reads require read-after-write and must go to primary/consistent path?

Keyset pagination

Continues after the last stable sort key instead of skipping an offset.

Use when: data is large/changing; encode sort key + tie-break ID in an opaque cursor.

Caching and search

Cache-aside

Application checks cache, loads source on miss, then populates cache. Writes update/invalidate after commit.

Always name: key, TTL, invalidation, source of truth and stale-data safety.

Versioned cache key

Includes a data/permission/model version so new writes naturally use a new key.

Benefit: reduces race-prone deletes; old entries expire later.

Search index

A denormalized projection optimized for text, filtering and ranking—not the authoritative mutation store.

Say: “Index updates are eventual; permissions/deletions need safe filtering and reconciliation.”

Cache stampede

Many requests miss the same key and all hit the source.

Mitigate: request coalescing/lock, jittered TTL, stale-while-revalidate or prewarming.

Materialized view

Precomputed data shaped for a read, such as Top-K or activity feed.

Trade-off: fast reads versus eventual update/rebuild complexity.

Denormalization

Copies selected fields into a read model to avoid joins/fan-out.

Say: which source is authoritative and how change/delete events reconcile copies.

Events, queues and asynchronous work

Event-driven architecture

A committed business fact is published so independent consumers update projections or trigger work.

Use when: secondary work can lag and benefits from decoupled scale/replay.

Message queue

Buffers work; consumers typically compete to process each message.

Use when: background jobs, retry and load smoothing are central.

Pub/Sub

Multiple subscribers receive a published event, often through separate subscriptions/consumer groups.

Use when: search, audit, notifications and analytics need the same fact independently.

Transactional outbox

Domain change and event-to-publish are written in one local transaction.

Solves: database/event dual-write gap; still produces at-least-once duplicates.

Idempotency

Repeating an operation with the same identity has no additional business effect.

Apply at: API request, consumer effect and external side-effect boundary.

Dead-letter queue

Quarantines messages that cannot succeed after bounded retries.

Needs: alert, inspection, correction and safe replay—not a silent graveyard.

Consistency and concurrency

Strong consistency

Reads observe a single current order/state according to the system’s guarantee.

Use for: core invariants, permissions, money-like state and atomic transitions.

Eventual consistency

Replicas/projections converge after a delay; users may see a stale intermediate view.

Use for: search, analytics, notifications and ranking—state the bound and UX.

Optimistic locking

Update succeeds only if the version/ETag is still current.

Use when: conflicts are uncommon and user think time makes locks impractical.

Pessimistic locking

Locks rows/resources before change to prevent competing writes.

Use for: short high-contention critical sections; avoid across network/user interactions.

At-least-once delivery

A message is retried until acknowledged and may arrive multiple times.

Design implication: idempotent consumers and deduplication.

Saga / compensation

Coordinates a multi-service workflow through local transactions and compensating actions.

Use when: one ACID transaction cannot span services; compensation may not fully undo reality.

Realtime communication

Polling

Client repeatedly requests current state.

Good for: simple low-frequency freshness; cost grows with empty polls.

Server-Sent Events (SSE)

Long-lived HTTP server-to-client stream with event IDs and straightforward reconnection.

Good for: feeds/status/domain updates that do not require bidirectional messages.

WebSockets

Persistent bidirectional connection.

Good for: chat/presence/collaboration; discuss auth, routing, heartbeat, backpressure and recovery.

Sequence/cursor recovery

Client records last applied event and requests missing changes after reconnect.

Fallback: if replay is unavailable/too large, send “resync required” and fetch snapshot.

Frontend architecture

Local UI state

Ephemeral interaction state such as open dialog, input text, drag target and focus.

Keep separate from: remote authoritative data.

Server state

Remote data with ownership, fetching, caching, freshness, retries and mutation lifecycle.

Use a query/cache layer: stable keys include tenant, filter and cursor.

Optimistic UI

Apply a predicted result before the server confirms.

Requires: operation ID, rollback snapshot, authoritative response and conflict policy.

Offline queue

Persists pending operations locally and retries on reconnect.

Requires: client IDs, idempotency, order/dependency model and conflict resolution.

Virtualization

Renders only visible portions of a large list/board.

Connect to backend: bounded pages, stable IDs and predictable heights/focus.

Code splitting

Loads application bundles/features on demand.

Use when: initial JS is a measurable bottleneck; prefetch likely next routes.

Security and access

Authentication

Establishes who the caller is.

Examples: session cookie, OAuth/OIDC token; validate issuer/audience/expiry.

Authorization

Determines what the authenticated actor can do with a resource.

Rule: enforce server-side on every authoritative path and sensitive result.

RBAC

Roles map to capabilities, often within tenant/project scope.

Good for: understandable enterprise administration; may need resource exceptions.

ABAC / policy

Decisions use attributes of actor, resource, action and context.

Trade-off: expressive but harder to cache, explain and audit.

CSRF

Tricks a browser into sending an authenticated state-changing request, especially with cookies.

Mitigate: same-site cookies, CSRF tokens and origin checks as appropriate.

XSS

Untrusted content executes script in the browser.

Mitigate: output encoding, safe rendering/sanitization, CSP and avoiding unsafe HTML.

Reliability and operations

Timeouts

Bound how long a dependency can consume request resources.

Set from: end-to-end latency budget; distinguish connect/read/deadline.

Retry with backoff + jitter

Retries transient failures while spacing clients to avoid synchronized storms.

Only retry: safe/idempotent operations and respect total deadline.

Circuit breaker

Stops repeated calls to a failing dependency and probes recovery.

Benefit: prevents cascade; needs meaningful fallback/degradation.

Observability

Metrics, logs and traces reveal health and explain customer impact.

Add: domain metrics and operation/event IDs, not only CPU and generic errors.

SLO

A target for customer-observed reliability/latency with an error budget.

Use to decide: alerting, rollout speed and reliability investment.

Canary / feature flag

Exposes a change to a controlled subset and supports rapid disable/rollback.

Pair with: compatible schema/contracts and measured success/error criteria.

Concept selection test

Before adding any component, answer:

  • Which stated requirement creates the need?
  • Which exact path or bottleneck does it improve?
  • What new failure mode or operational cost does it introduce?
  • What is the source of truth?
  • What happens when this component is unavailable?
  • How will I measure that it is working?
