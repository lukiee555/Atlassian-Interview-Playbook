1. Real-time chat system

Reported in 2026 full-stack experienceFrontend-heavy

Question shape

Design a real-time chat experience with message history, delivery/read receipts, presence, offline resilience and scalable connections.

What is being tested

Communication choice, client optimistic state, message identity/order, WebSocket lifecycle, offline persistence, idempotency and backend partitioning.

Expected approach

  1. Clarify one-to-one versus group, attachments, history, receipts, presence and ordering.
  2. Generate clientMessageId before send; render locally as pending.
  3. Use WebSocket for live delivery and HTTPS for history/large uploads.
  4. Partition durable messages by conversation ID; assign per-conversation sequence.
  5. Retry with the same message ID; deduplicate at the server.
  6. Persist pending/recent state in IndexedDB and catch up after the last sequence.

Likely follow-ups

How do you preserve ordering?

Guarantee order within one conversation, not globally. Use a server-assigned conversation sequence and display provisional client messages until acknowledged/reconciled.

How do you handle multiple devices?

Each device has its own connection/cursor; server fan-out targets active devices. Read state is a user/conversation projection and updates idempotently by sequence/time.

What should not be stored with messages?

Presence and typing are ephemeral best-effort state. Keep durable message history separate.

Common mistakes

Claiming global ordering, using only WebSocket without history recovery, omitting client-generated IDs, treating presence as perfectly consistent, or ignoring slow-client backpressure.

2. Notion / Confluence-style notes application

Reported in full-stack interview listings

Question shape

Design a page/block-based note-taking application with hierarchy, autosave, search, sharing, version history and optionally real-time collaboration.

What is being tested

Document model, frontend editor state, autosave, block ordering, permissions, search indexing, offline/conflict strategy and the judgment to avoid CRDTs until required.

Expected approach

  1. Scope create/edit pages, page tree, blocks, sharing and search.
  2. Model Page and ordered Block entities; use rank keys for block reorder.
  3. Use local editor state plus debounced versioned autosave.
  4. Store snapshots/deltas for version history based on scale and restore needs.
  5. Publish update events to search and realtime collaboration projections.
  6. Start with optimistic concurrency or block-level conflict; introduce OT/CRDT only for simultaneous character editing.

Likely follow-ups

How would two people edit the same paragraph?

Clarify whether simultaneous character-level editing is required. For it, use an OT/CRDT-based operation model and session service; for simpler collaboration, block-level version conflicts may be sufficient.

How do permissions inherit through page hierarchy?

Define parent inheritance plus explicit overrides, compute/evaluate policy with versioned caches, and invalidate descendants on policy changes. Search results still require permission safety.

How do you autosave without overloading the backend?

Debounce/coalesce local changes, send operation/version batches, retry idempotently and persist pending edits locally.

Common mistakes

Storing an entire giant document blob for every keystroke, introducing CRDTs without requirement, ignoring page-tree permissions, or claiming search is immediately consistent with the source.

3. Distributed job scheduler

Older Atlassian-reported design questionRecurring jobs

Question shape

Design a scheduler that executes recurring work—for example a job every ten minutes—with retries, status, cancellation and distributed workers.

What is being tested

Due-job indexing, distributed claiming/leases, at-least-once execution, idempotent effects, retries, dead-letter handling, recurring-time semantics and observability.

Expected approach

  1. Store job definition, next run time, schedule/timezone, status and version.
  2. Scheduler instances claim due jobs atomically through row locking/compare-and-set lease.
  3. Enqueue an execution with unique ID; workers heartbeat and acknowledge.
  4. Use at-least-once delivery and require idempotent handlers.
  5. On failure, exponential backoff and bounded retries, then dead-letter/manual action.
  6. Compute the next occurrence from schedule policy; handle DST explicitly.

Likely follow-ups

Worker completes the side effect but crashes before acknowledgment?

The execution is redelivered. The handler uses an idempotency key or side-effect record so the repeated delivery returns the prior result rather than repeating the effect.

Millions of jobs fire at 9:00 AM?

Shard due-job index, distribute queue partitions, reserve capacity/priority, apply tenant quotas and allow a bounded scheduling delay if the SLA permits.

Exactly once?

Explain why the practical target is at-least-once delivery with effectively-once business effects.

Common mistakes

One scheduler process scanning the entire table, no lease expiry, claiming exactly-once, no idempotency or ignoring timezone/DST.

4. Google Sheets-style collaborative application

Candidate-reported system-design topic

Question shape

Design a spreadsheet-like web application, including client-server flow, APIs, data model, formulas/queries, collaboration and optimization.

What is being tested

Sparse data model, large-grid rendering, formula dependency graph, recalculation, batch updates, collaboration and separation of durable cell state from ephemeral selection/presence.

Expected approach

  1. Scope workbook/sheets/cells, formulas, sharing and collaboration.
  2. Store sparse non-empty cells keyed by sheet/row/column; version updates.
  3. Maintain a formula dependency graph and recalculate affected cells in topological order; detect cycles.
  4. Virtualize rows/columns in the browser and fetch visible ranges/chunks.
  5. Batch edits and stream committed changes; recover by version/sequence.
  6. Move heavy recalculation to workers while preserving deterministic results.

Likely follow-ups

How do you represent a million-by-million grid?

Store sparse cells, not every coordinate. Fetch and render visible ranges, cache chunks and maintain dimensions/format metadata separately.

How do formulas update?

Parse dependencies, update graph, detect cycles and recalculate only transitive dependents. Version computations so stale async results cannot overwrite newer input.

Common mistakes

Materializing the entire grid, rendering every cell, recalculating the whole workbook on each edit, or ignoring circular references and concurrent changes.

5. Social-media-style feed or content system

Reported in a P50 backend experience

Question shape

Design a social-media-like application or feed; candidate reports mention discussion of tables, database choice, APIs, pagination, indexing and user experience.

What is being tested

Access-pattern-driven schema, feed generation, cursor pagination, indexes, fan-out strategy and ability to connect backend decisions to the user experience.

Expected approach

Clarify follow model, timeline ordering, posting, likes/comments and personalization. Start with pull-on-read for moderate scale; consider fan-out-on-write for normal users and pull/merge for high-fan-out accounts. Use stable cursor ordering, materialized candidates and eventual counters.

Common mistakes

Offset pagination on a changing feed, synchronous fan-out to millions of followers, one database choice without access patterns, or no strategy for deleted/private content.

6. Browser-to-backend request and authentication flow

Reported full-stack craft discussionDiscussion topic

Question shape

Explain what happens when a user logs in, clicks checkout/pay, or performs another web action—from DOM event and validation through DNS/TLS, API, authentication, backend services, database and rendering.

What is being tested

Breadth, sequencing, authentication versus authorization, tokens/cookies, CSRF/XSS, request IDs, backend processing, data fetching, state updates and failure UX.

Expected approach

Browser eventHandler, client validation, disabled/retry state and idempotency key for high-risk action.
NetworkDNS, connection/TLS, HTTP request, headers/cookie/token.
EdgeCDN/WAF/gateway, rate limit, request/trace ID.
ApplicationAuthenticate, authorize, validate, service transaction and downstream calls.
ResponseStatus/body, cache semantics, state reconciliation, accessibility and error/unknown-outcome handling.

Common mistakes

Mixing authentication with authorization, storing long-lived tokens carelessly, ignoring CSRF for cookie auth, double-submitting a payment, or ending at “API returns JSON” without frontend reconciliation.

7. Critique an existing architecture

Candidate-reported architecture review

Question shape

You are shown an existing multi-service diagram and asked to find flaws or evolve it. Candidate reports mention separate load balancers, shared databases, server-local authentication/logging and queue/external-service failures.

What is being tested

Ability to reason from failure modes rather than redraw everything, identify single points of failure/coupling, and prioritize changes by customer risk.

Expected approach

  1. Ask for the system goal, SLO and known pain.
  2. Trace one request and one failure path.
  3. Classify risks: correctness/security, availability, scale, operability and maintainability.
  4. Prioritize the highest-impact issue and propose incremental remediation.
  5. State migration/rollout and metrics—not only the destination diagram.

Common mistakes

Calling every shared component “bad,” replacing technology without evidence, missing auth/data ownership, or proposing a complete rewrite without migration.
