Fix the password functionality in a backend web application

The strongest response begins with evidence: reproduce the failure, trace registration/login/reset paths, identify the first divergence, then patch the correct security boundary and add a regression test.

Evidence boundary

A public candidate report disclosed a small backend website with broken password functionality and follow-ups about file placement and frontend/backend validation. It did not disclose the root cause. This page uses a representative Spring bug: encoding the submitted password again and comparing hash strings, which fails with salted encoders such as BCrypt. Treat it as realistic practice, not the verified hidden task.

Interviewer question

Interviewer
“The password functionality in this application is broken. Please investigate and fix it using the available AI assistant.”

What should I think about first?

Think

“Password functionality” is not a precise root cause. It could mean registration, login, password change, reset, confirmation, frontend validation, hashing configuration, database migration or error mapping. I should not ask the agent to replace the whole authentication stack.

  1. Reproduce the reported behaviour or identify the failing test.
  2. Determine which flow is affected and whether other password flows still work.
  3. Trace raw input → validation → service → encoder → stored hash → response.
  4. Find the first point where actual behaviour differs from expected.
  5. Write a regression test that fails for that reason before broad implementation.
I’ll first reproduce the failure and narrow it to registration, authentication, update or reset. Then I’ll trace how the raw password and stored hash are handled, verify the configured encoder and existing error contract, and make the minimum fix. I won’t change security code based only on an AI guess.

Representative root cause

Identify the problem

The login service encodes the submitted password again and compares the resulting String with the stored BCrypt hash. BCrypt generates a new salt on each encode, so two hashes of the same password are normally different.

Broken implementation

// Broken: a fresh BCrypt salt produces a different encoded value.
String candidateHash = passwordEncoder.encode(request.password());
if (!candidateHash.equals(user.getPasswordHash())) {
    throw AuthenticationException.invalidCredentials();
}

Evidence, not intuition

PasswordEncoder encoder = new BCryptPasswordEncoder();
String stored = encoder.encode("correct-horse");
String encodedAgain = encoder.encode("correct-horse");

assert !stored.equals(encodedAgain);       // Different salts
assert encoder.matches("correct-horse", stored); // Correct API

Minimum safe fix

Use the configured PasswordEncoder.matches(raw, encoded) method at the authentication boundary. Preserve registration’s “encode once before storage” behaviour and the existing generic error response.

package com.example.auth;

import java.util.Locale;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;

@Service
public final class AuthenticationService {
    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;
    private final TokenService tokenService;

    public AuthenticationService(
            UserRepository userRepository,
            PasswordEncoder passwordEncoder,
            TokenService tokenService) {
        this.userRepository = userRepository;
        this.passwordEncoder = passwordEncoder;
        this.tokenService = tokenService;
    }

    public AuthenticationResult authenticate(LoginRequest request) {
        String normalizedEmail = request.email()
                .trim()
                .toLowerCase(Locale.ROOT);

        User user = userRepository.findByEmail(normalizedEmail)
                .orElseThrow(AuthenticationException::invalidCredentials);

        if (!passwordEncoder.matches(
                request.password(), user.getPasswordHash())) {
            throw AuthenticationException.invalidCredentials();
        }

        return tokenService.issueFor(user);
    }
}
Why the generic error remains

Returning the same “invalid credentials” result for an unknown user and a wrong password reduces account-enumeration information and preserves the existing client contract.

Registration remains “encode once”

public User register(RegisterRequest request) {
    passwordPolicy.validate(request.password());

    String passwordHash = passwordEncoder.encode(request.password());
    User user = User.create(request.email(), passwordHash);

    return userRepository.save(user);
}

Password change keeps responsibilities separate

@Transactional
public void changePassword(UserId userId, ChangePasswordRequest request) {
    User user = userRepository.getRequired(userId);

    if (!passwordEncoder.matches(
            request.currentPassword(), user.getPasswordHash())) {
        throw AuthenticationException.invalidCredentials();
    }

    passwordPolicy.validate(request.newPassword());
    user.replacePasswordHash(
            passwordEncoder.encode(request.newPassword()));

    // Apply the repository's existing session-revocation policy if required.
}

Which file should contain the password logic?

Interviewer follow-up
“Which file would you place the password logic in?”
I would first separate three concerns. Request-shape validation can live on the DTO/schema. Reusable password-policy rules belong in the existing policy/domain validator. Hashing and password comparison belong in the authentication or user-credential service using the repository’s configured PasswordEncoder. The controller should orchestrate transport and map errors, not implement hashing. I would follow the current project structure rather than add a new layer unnecessarily.

Why both frontend and backend validation?

Interviewer follow-up
“Why do you need both backend and frontend validation?”
Frontend validation improves the user experience with immediate field-level feedback and avoids unnecessary requests. Backend validation enforces the real invariant because the UI can be bypassed, modified or outdated, and other clients can call the API directly. The backend remains authoritative. I would mirror only safe, user-helpful rules in the frontend and keep authorization, hashing, database-dependent checks and abuse controls on the backend.

Regression tests

package com.example.auth;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.mockito.Mockito.when;

import java.util.Optional;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.mockito.Mockito;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

class AuthenticationServiceTest {
    private UserRepository users;
    private TokenService tokens;
    private PasswordEncoder encoder;
    private AuthenticationService service;

    @BeforeEach
    void setUp() {
        users = Mockito.mock(UserRepository.class);
        tokens = Mockito.mock(TokenService.class);
        encoder = new BCryptPasswordEncoder();
        service = new AuthenticationService(users, encoder, tokens);
    }

    @Test
    void authenticatesWhenRawPasswordMatchesStoredHash() {
        User user = User.testUser(
                "person@example.com",
                encoder.encode("correct-horse"));
        AuthenticationResult expected =
                new AuthenticationResult("session-token");

        when(users.findByEmail("person@example.com"))
                .thenReturn(Optional.of(user));
        when(tokens.issueFor(user)).thenReturn(expected);

        AuthenticationResult actual = service.authenticate(
                new LoginRequest("Person@Example.com", "correct-horse"));

        assertEquals(expected, actual);
    }

    @Test
    void rejectsWrongPassword() {
        User user = User.testUser(
                "person@example.com",
                encoder.encode("correct-horse"));
        when(users.findByEmail("person@example.com"))
                .thenReturn(Optional.of(user));

        assertThrows(AuthenticationException.class,
                () -> service.authenticate(
                        new LoginRequest(
                                "person@example.com", "wrong-password")));
    }

    @Test
    void usesSameFailureForUnknownUser() {
        when(users.findByEmail("missing@example.com"))
                .thenReturn(Optional.empty());

        assertThrows(AuthenticationException.class,
                () -> service.authenticate(
                        new LoginRequest(
                                "missing@example.com", "anything")));
    }
}

Testing order

  1. Run the existing failing test or reproduce the request before editing.
  2. Add the regression test that stores a real BCrypt hash and authenticates with the raw password.
  3. Run wrong-password and unknown-user cases.
  4. Run controller/integration tests to preserve status and body.
  5. Run the broader authentication suite, then the project suite if time permits.

Security and correctness checklist

  • The raw password is never logged, persisted or included in an exception.
  • The configured encoder is injected; no custom cryptography is introduced.
  • Registration/update encode once; authentication uses matches.
  • Unknown-user and wrong-password responses preserve the same external contract.
  • Frontend validation is not treated as authoritative.
  • Rate limiting and monitoring remain in their existing boundaries.
  • Password reset tokens are outside this fix unless evidence points there.
  • The diff contains no accidental secret, test credential or verbose payload logging.

Common mistakes

  • Changing multiple auth flows before reproducing the bug.
  • Comparing raw and encoded strings directly.
  • Encoding the submitted password and expecting the encoded strings to match.
  • Replacing BCrypt or changing strength/configuration without a requirement or migration plan.
  • Returning “email not found” for one path and “wrong password” for another.
  • Implementing password policy, hashing and token issuance in the controller.
  • Logging the request body while debugging.
  • Mocking PasswordEncoder.matches so completely that the regression test cannot catch the real bug.
  • Letting AI rewrite authentication configuration or add a security library unnecessarily.

Interviewer follow-ups

Why does encoding the same password twice produce different strings?

Salted password encoders generate a fresh random salt for each encode. The stored hash contains the parameters and salt needed for the encoder to verify the raw password through matches. Direct String equality is the wrong operation.

Should password policy be in the frontend, DTO or service?

Frontend: immediate UX. DTO: simple shape such as required/minimum length where the project uses schema validation. Service/domain policy: authoritative reusable business rule. Hashing/comparison: credential/authentication service. Avoid one controller owning the rule.

Would you reveal which password rule failed?

During new-password creation, specific policy guidance is often useful. During authentication, use a generic invalid-credentials result. Follow the product’s security policy and current error contract.

How would you handle existing hashes created with an older encoder?

I would inspect whether the configured delegating encoder can identify versions. A common strategy is verify with the supported old format and rehash using the current format after a successful login. That requires an explicit migration requirement and tests; I would not improvise it in this bug fix.

What happens after a password change?

Clarify the product policy. Security-sensitive systems often revoke other sessions or bump a credential version used during token validation. The current session may remain or be re-authenticated. Implement the repository’s established policy, not a new one hidden in this fix.

How do you avoid timing or account-enumeration differences?

Keep the external response generic. Some systems perform a dummy hash verification for missing users to reduce large timing differences, but that should follow the existing security design and threat model rather than be added speculatively.

How would you test the frontend and backend rule together?

Unit-test frontend validation for immediate feedback, backend policy/service tests for authority, and one contract or end-to-end path for the request/response shape. Do not duplicate every case at every layer.

What if the AI suggests storing encrypted passwords so they can be recovered?

I would reject it. Passwords should be stored using a purpose-built one-way password hash/encoder, not reversible encryption. A reset flow sets a new password; it should not recover the old one.

How would you handle repeated login attempts?

Rate limiting, progressive delay, monitoring and product-specific lockout are defence-in-depth. They belong in existing gateway/auth-abuse components and must avoid becoming an account-denial vector. They do not replace correct password verification.

Final diff review

Password-specific reviewer prompt

Review the current diff only. Verify that registration/update encode raw passwords once, login compares with the configured PasswordEncoder.matches method, no raw secret is logged or stored, unknown-user and wrong-password responses remain externally equivalent, controller/service responsibilities match repository conventions, regression tests exercise a real encoded hash, and no unrelated security configuration changed. Cite a concrete failure for each concern.

What I would say after the fix

I reproduced the login failure and traced it to the authentication service. The stored value was a BCrypt hash, but the code encoded the submitted password again and compared the two hash strings. Because BCrypt uses a fresh salt, that comparison fails even for the correct password. I replaced it with the configured PasswordEncoder.matches call, preserved generic invalid-credentials behaviour and left registration’s encode-once path unchanged. I added a regression test with a real BCrypt hash, wrong-password and unknown-user cases, ran the relevant controller/authentication suite, and reviewed the diff for secret logging or unrelated config changes.

Question-specific AI prompts

Trace all credential paths

Do not edit. Map registration, login, password change and reset from request to persistence. Show where a raw password first enters, where policy validation occurs, where an encoded hash is created, where comparison occurs, and where errors are mapped. Flag raw-secret logging or direct String comparison.

Prove the suspected BCrypt bug

Do not patch yet. Using the repository’s configured PasswordEncoder and test framework, create the smallest test or reproducible snippet that demonstrates the observed failure and distinguishes encode-and-compare from matches(raw, encoded). Do not print the raw password or full hash.
