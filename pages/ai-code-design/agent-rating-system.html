Interviewer question - AI-enabled version

Interviewer
You have an existing Java support-service repository containing tickets and agents. Extend it so a customer can rate the agent who handled a resolved ticket. Add a leaderboard ordered by average rating. The implementation should be test-driven, fit the current architecture, and remain correct under follow-up requirements such as deterministic ties, monthly rankings and concurrent submissions.

What should I think about first?

Think
  1. Define the rating invariant. Score range, eligible ticket state, who may submit, one rating versus edits, and whether a ticket can rate only its assigned agent.
  2. Define ranking semantics before sorting. Average alone creates unstable ties. Decide secondary order, minimum-rating threshold and precision.
  3. Separate source facts from projections. Individual ratings are the durable facts; average and leaderboard are derived views.
  4. Make time explicit. Monthly ranking needs a clock, time zone and half-open date range.
  5. Use the repository, not a memorized design. First locate existing ticket authorization, persistence, exceptions and tests.
I will first confirm who can rate which ticket, whether ratings are immutable or editable, the score range, tie-breaking and monthly time-zone semantics. Then I will trace the existing ticket-completion flow, capture the behavior with focused failing tests, make the smallest architectural change, and only then discuss the concurrency and scaling follow-ups.

Acceptance criteria

  • A customer can rate only a resolved ticket they own and only the agent assigned to that ticket.
  • A rating score must be an integer from 1 through 5.
  • The same ticket cannot create two ratings, including concurrent duplicate requests.
  • The leaderboard is tenant-scoped and ordered by average descending, count descending, then stable agent ID ascending.
  • A monthly query includes ratings whose timestamp is greater than or equal to the month start and less than the next month start.
  • Invalid requests use the repository's existing error and authorization contracts.
  • Focused and relevant regression tests pass, and the final diff contains no unrelated refactor.

Compare approaches before implementation

ApproachStrengthCost/riskWhen to choose
Store immutable ratings; aggregate on readSimple source of truth, easy correction and monthly query.Expensive leaderboard at large scale.Best first implementation when scale is moderate or repository already supports aggregate SQL.
Update an aggregate row transactionally on every ratingVery fast reads.Concurrent update complexity; edits/deletes require correction logic.When low-latency leaderboard is strict and database supports atomic update/versioning.

For the initial repository change I would keep each rating as the durable fact and use the existing database to aggregate the small leaderboard query. That is easiest to prove and correct. If read volume or cardinality makes it too slow, I would add an asynchronous projection without changing the rating contract.

Representative Java design

Domain records

package com.example.support.rating;

import java.time.Instant;
import java.util.UUID;

public record AgentRating(
        UUID ticketId,
        UUID tenantId,
        UUID agentId,
        UUID customerId,
        int score,
        Instant submittedAt) {

    public AgentRating {
        if (score < 1 || score > 5) {
            throw new InvalidRatingException("Rating must be between 1 and 5");
        }
    }
}
package com.example.support.rating;

import java.math.BigDecimal;
import java.math.RoundingMode;
import java.util.UUID;

public record AgentScore(UUID agentId, long scoreSum, long ratingCount) {
    public BigDecimal average() {
        if (ratingCount == 0) {
            return BigDecimal.ZERO;
        }
        return BigDecimal.valueOf(scoreSum)
                .divide(BigDecimal.valueOf(ratingCount), 2, RoundingMode.HALF_UP);
    }
}

Service orchestration

package com.example.support.rating;

import java.time.Clock;
import java.time.Instant;
import java.time.YearMonth;
import java.time.ZoneId;
import java.util.List;
import java.util.UUID;

public final class AgentRatingService {
    private final TicketRepository tickets;
    private final RatingRepository ratings;
    private final Clock clock;

    public AgentRatingService(
            TicketRepository tickets,
            RatingRepository ratings,
            Clock clock) {
        this.tickets = tickets;
        this.ratings = ratings;
        this.clock = clock;
    }

    public void submitRating(
            UUID ticketId,
            UUID authenticatedCustomerId,
            int score) {
        Ticket ticket = tickets.findRequired(ticketId);
        ticket.requireResolved();
        ticket.requireOwnedBy(authenticatedCustomerId);

        AgentRating rating = new AgentRating(
                ticket.id(),
                ticket.tenantId(),
                ticket.assignedAgentId(),
                authenticatedCustomerId,
                score,
                Instant.now(clock));

        // Back this with a unique database key on ticket_id.
        ratings.insert(rating);
    }

    public List<AgentScore> monthlyLeaderboard(
            UUID tenantId,
            YearMonth month,
            ZoneId tenantZone,
            int limit) {
        Instant start = month.atDay(1).atStartOfDay(tenantZone).toInstant();
        Instant end = month.plusMonths(1)
                .atDay(1)
                .atStartOfDay(tenantZone)
                .toInstant();

        return ratings.summarize(tenantId, start, end, limit);
    }
}

Database ordering

CREATE UNIQUE INDEX uq_agent_rating_ticket
    ON agent_rating(ticket_id);

SELECT
    agent_id,
    SUM(score) AS score_sum,
    COUNT(*) AS rating_count,
    CAST(SUM(score) AS DECIMAL) / COUNT(*) AS average_score
FROM agent_rating
WHERE tenant_id = :tenant_id
  AND submitted_at >= :start_instant
  AND submitted_at < :end_instant
GROUP BY agent_id
ORDER BY
    average_score DESC,
    rating_count DESC,
    agent_id ASC
LIMIT :limit;
Why the unique database key matters

Two requests can both pass an application-level exists check before either inserts. The database uniqueness constraint is the final authority. Translate the duplicate-key exception into the existing idempotent/conflict response instead of relying on a process-local lock.

Focused JUnit tests

class AgentRatingServiceTest {
    private final Clock clock = Clock.fixed(
            Instant.parse("2026-10-07T10:00:00Z"), ZoneOffset.UTC);
    private final FakeTicketRepository tickets = new FakeTicketRepository();
    private final InMemoryRatingRepository ratings = new InMemoryRatingRepository();
    private final AgentRatingService service =
            new AgentRatingService(tickets, ratings, clock);

    @Test
    void resolvedTicketOwnerCanRateAssignedAgent() {
        Ticket ticket = tickets.saveResolvedTicketFor(CUSTOMER_ID, AGENT_ID, TENANT_ID);

        service.submitRating(ticket.id(), CUSTOMER_ID, 5);

        assertThat(ratings.findByTicket(ticket.id()))
                .get()
                .extracting(AgentRating::agentId, AgentRating::score)
                .containsExactly(AGENT_ID, 5);
    }

    @Test
    void rejectsSecondRatingForSameTicket() {
        Ticket ticket = tickets.saveResolvedTicketFor(CUSTOMER_ID, AGENT_ID, TENANT_ID);
        service.submitRating(ticket.id(), CUSTOMER_ID, 4);

        assertThatThrownBy(() ->
                service.submitRating(ticket.id(), CUSTOMER_ID, 5))
                .isInstanceOf(DuplicateRatingException.class);
    }

    @Test
    void leaderboardUsesDeterministicTieBreakers() {
        ratings.save(TENANT_ID, AGENT_A, 5, OCT_1);
        ratings.save(TENANT_ID, AGENT_A, 3, OCT_2); // average 4, count 2
        ratings.save(TENANT_ID, AGENT_B, 4, OCT_3); // average 4, count 1
        ratings.save(TENANT_ID, AGENT_C, 5, OCT_4); // average 5

        List<AgentScore> result = service.monthlyLeaderboard(
                TENANT_ID, YearMonth.of(2026, 10), ZoneOffset.UTC, 10);

        assertThat(result).extracting(AgentScore::agentId)
                .containsExactly(AGENT_C, AGENT_A, AGENT_B);
    }
}

Likely P40 follow-ups

What if customers can edit a rating?

Decide whether the fact is mutable or versioned. A direct update must correct both sum and count atomically; an event model can append RatingChanged and rebuild projections. Keep a unique ticket identity and audit the previous value.

How do you handle simultaneous ratings for the same ticket?

Use a unique database constraint on ticket ID inside a transaction. One insert succeeds; the other becomes a deterministic duplicate/conflict result. An application pre-check improves the message but is not the concurrency guarantee.

How would you make leaderboard reads fast?

Keep immutable rating facts, publish an outbox event, and maintain a tenant/month materialized score projection. Store sum and count, not only average, so updates and recomputation remain correct. Define freshness and rebuild/reconciliation.

How would you prevent an agent with one five-star rating always winning?

This is product policy. Options include a minimum count, Bayesian average, Wilson score or separate confidence indicator. Do not silently invent it; ask for the intended fairness rule and make it configurable/tested.

What if an agent changes team or tenant?

Ratings should retain the tenant/team context at submission time if historical rankings must be stable. Current-profile joins are fine for display metadata, but should not rewrite historical ownership accidentally.

Why not store only the current average?

An average alone cannot be updated correctly without count, cannot explain/rebuild history, and makes monthly windows impossible. Preserve rating facts or at least sum and count plus a replayable source.

What happens when the month changes?

Make month a first-class query/projection key. Do not clear a global leaderboard destructively. Start the new window while retaining previous months for audit and late-event policy.

Common mistakes

  • Sorting a double average without defining precision or deterministic ties.
  • Checking duplicates in Java and assuming that prevents concurrent double inserts.
  • Allowing ratings before ticket resolution or for another customer's ticket.
  • Storing only an average and losing the source/count required for correction.
  • Using the server's default time zone for monthly boundaries.
  • Building Kafka, Redis and multiple services before proving the small repository change.
  • Letting AI generate a broad refactor that you cannot explain.

Two-minute closing summary

I added the rating invariant through the existing ticket service path and captured it with focused tests before production changes. The durable source is one immutable rating per resolved ticket, protected by database uniqueness. The leaderboard aggregates by tenant and month with explicit half-open time boundaries and deterministic tie-breaking. I kept the first implementation simple and synchronous; at higher read scale I would project sum and count asynchronously from rating events. I ran the focused and neighboring tests, reviewed the diff, and the remaining design choice is the product policy for minimum sample size.
