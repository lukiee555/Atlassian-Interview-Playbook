Concepts behind a safe repository change

Use these ideas to explain why your code belongs where it does, why your tests are sufficient, and why an AI-generated edit should—or should not—be accepted.

Repository mapping

Entry point

The route, controller, command handler, event listener or UI action where the behaviour begins.

Say: “I’m locating the real entry point before assuming which class owns the behaviour.”

Execution path

The ordered call flow from input to side effect and response. It reveals validation boundaries and bypass routes.

Say: “I want to know every path that can create or update this state.”

Repository convention

The closest existing feature is usually stronger evidence than a generic framework pattern.

Say: “I’ll follow the current error and test style unless the task requires changing it.”

Baseline

The state of tests and application behaviour before your edit. Without it, you may claim an existing failure as your regression.

Say: “This test already fails before my change; I’ll keep it separate from the task evidence.”

Validation boundaries

Ask

Can another client or code path bypass this layer? If yes, that layer cannot be the sole authority for the invariant.

Frontend validation improves usability. Backend validation protects the system from direct API calls, modified clients, stale clients and internal code paths. Database constraints protect integrity during races and programming mistakes where the rule can be expressed safely.

A useful sentence

“I’ll mirror this rule in the UI for immediate feedback, but the backend remains authoritative. Where a persistence constraint can prevent a race, I’ll use that as a final integrity boundary rather than as the user experience.”

Smallest safe change

The smallest safe change is not always the fewest lines. It is the narrowest set of edits that makes the new behaviour correct across all relevant paths and proves it with tests.

  • Modify existing extension points before creating a parallel framework.
  • Preserve API and data compatibility unless the requirement explicitly changes them.
  • Avoid introducing a dependency for logic that can be expressed clearly with existing tools.
  • Do not combine the requested feature with cleanup that can be reviewed separately.
  • Prefer one authoritative rule reused by create/update/reset paths over copied conditions.

Testing layers

Unit test

Proves a small rule or service branch quickly. Best for PIN policy, password comparison and error mapping in isolation.

Use when: the behaviour is deterministic and dependencies can be controlled.

Integration test

Proves wiring between HTTP, validation, service, security configuration and persistence.

Use when: the bug could live at a framework boundary.

End-to-end test

Proves a critical user flow through the running application but is slower and more fragile.

Use when: the repository already has this layer and the change crosses UI/API boundaries.

Regression test

Fails on the original bug and passes after the fix. It is the strongest compact evidence that the root cause is addressed.

Say: “I’ll first write or identify the test that reproduces the reported failure.”

P40 LLD reasoning patterns

Deterministic contract

Ordering, tie-breakers, wildcard precedence, boundary behavior and error semantics must be explicit rather than accidental.

Examples: rating ties, exact route over wildcard, wall collision, N versus N+1 requests.

Time as a dependency

Monthly leaderboards and rate-limit windows are not reliably testable when production code reads the wall clock directly.

Show it: inject a Clock/time source and advance it without sleeping.

Atomic state transition

A concurrent collection does not make a multi-step read/check/write sequence atomic.

Show it: database uniqueness, transaction, compare-and-set or per-key compute.

Ordered state + membership

Stateful simulations often need both order and O(1) membership checks.

Examples: Snake uses a deque for body order plus a set for collision membership.

Data structure from access pattern

Choose the simplest structure that satisfies the observed route count, lookup frequency, update frequency and complexity target.

Examples: list scan versus segment Trie; computed leaderboard versus projection.

Compatibility before cleverness

An extension is not correct if it silently changes exact routes, error contracts, existing callers or persistence semantics.

Show it: run old tests first and last; keep the public API stable unless asked.

AI review concepts

Hallucinated repository facts

An assistant may describe a file or function that does not exist. Require paths and symbols, then open them yourself.

Scope drift

The agent may refactor neighbouring code, add libraries or change public types. Inspect the diff after every bounded step.

Tests that pass for the wrong reason

A mock can bypass the changed branch; an assertion may be too broad; the test command may not discover the new file. Read test output and coverage of behaviour, not merely the exit code.

Confident security mistakes

Never accept custom password hashing, raw-secret logging, reversible encryption or client-only enforcement because the generated code looks polished.

Unexplainable code

If you cannot explain an abstraction, library call or concurrency choice, pause and ask the assistant to explain it from this repository—or simplify it.

Password-specific fundamentals

  • Store a password hash, never the raw password.
  • Use the configured password encoder’s matches(raw, encoded) API; do not encode again and compare strings.
  • Do not log passwords, reset tokens or full authentication payloads.
  • Use generic authentication failures where exposing account existence would be harmful.
  • Keep policy validation separate from hashing/comparison responsibilities.
  • Rate limiting, lockout and monitoring are defence-in-depth concerns, not substitutes for correct comparison.

How to explain AI usage

I used Plan mode to map the request flow and identify existing conventions. I verified the cited files myself, then constrained Agent mode to the agreed classes. The agent initially suggested [specific thing], which I rejected because [repository evidence or risk]. I ran the tests directly, inspected the final diff and can explain each change.
Use concepts as explanations, not buzzwords.
