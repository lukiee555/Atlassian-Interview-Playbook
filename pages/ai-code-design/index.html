AI-Enabled Code Design

The task is not “make AI produce code.” It is to understand an unfamiliar repository, define the requirement, direct the assistant, verify its work, and leave behind a small, defensible change.

The mental model

Clarify the ticketTurn one sentence into explicit acceptance criteria and identify ambiguous business rules.
Establish a baselineRead the README/build files, run the relevant test command and record pre-existing failures.
Map the execution pathRequest/route → DTO/schema → controller/handler → service/domain → repository → error response.
Plan before editingName the files, behaviour, tests and risk. Use Plan mode as a reviewer, not an oracle.
Implement a narrow vertical sliceFollow current conventions and avoid new abstractions or dependencies without evidence.
Verify and explainRun tests, inspect the diff, challenge the AI output and explain every changed line.

What the interviewer is likely observing

Requirement judgment

Do you notice leading zeroes, existing data, error contracts, update flows, retries and security implications?

Show it: restate the rule and ask only high-value clarifications.

Repository comprehension

Can you find the real control flow and distinguish relevant files from generated or unrelated code?

Show it: cite symbols and run the existing application/tests.

Architectural placement

Can you separate request-shape validation, business invariants, security logic, orchestration and persistence?

Show it: say why the rule belongs where you place it.

AI collaboration

Can you scope prompts, spot incorrect assumptions, reject unnecessary edits and preserve ownership?

Show it: narrate why you accept or reject each suggestion.

Testing discipline

Can you prove the new behaviour and protect existing behaviour without building a huge suite?

Show it: baseline, focused tests, negative cases, broader suite.

Diff quality

Does the final change avoid formatting churn, hidden interface changes, debug logging and speculative refactoring?

Show it: review the diff aloud before declaring success.

A practical 60-minute structure

0–5 min

Understand and clarify

Restate the requirement, ask two to four material questions and define success.

5–12 min

Run the baseline

Read README/build files, execute tests, inspect structure and note existing failures.

12–18 min

Trace and plan

Locate the relevant flow, state the smallest change and identify the tests.

18–38 min

Implement

Use bounded Agent prompts or edit directly. Review each file immediately.

38–50 min

Test and debug

Run focused tests, add edge cases and investigate failures with evidence.

50–60 min

Review and summarize

Inspect the diff, explain placement/trade-offs, state test evidence and remaining risk.

What to say at the start

I’ll first confirm the expected behaviour and any important edge cases. Then I’ll establish a baseline, trace the current request flow and identify the repository’s existing conventions. I’ll use the assistant to accelerate discovery and implementation, but I’ll review its assumptions and verify the result with tests and the final diff.

How to use AI without disappearing from the interview

Use AI forYou still ownWeak behaviour
Repository map, call graph, unfamiliar syntaxRequirement interpretation and evidence checksAccepting a guessed file path or architecture
Drafting a focused implementationScope, placement, API/error compatibility“Fix everything and make tests pass”
Generating targeted testsChoosing meaningful cases and reading outputBelieving “tests pass” without running them
Reviewing the diffFinal judgment and explanationShipping code you cannot defend

Final review checklist

  • The implementation satisfies the exact acceptance criteria—not a broader guessed requirement.
  • The rule is placed in the repository’s existing architectural layer.
  • Existing API shapes, status codes and error messages remain compatible unless the task requires change.
  • Null, empty, malformed, duplicate and boundary inputs are considered.
  • Focused tests and the relevant broader suite were actually run.
  • No unrelated files, dependencies, formatting or generated artefacts changed.
  • You can explain what the AI suggested, what you changed and what you rejected.
