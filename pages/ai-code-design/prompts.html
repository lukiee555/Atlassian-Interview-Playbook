AI prompts that preserve your ownership

Use the assistant as a repository explorer, implementation partner and skeptical reviewer. Keep each request bounded, evidence-based and easy to verify.

On this page
Do not paste the entire sequence automatically

Choose the next prompt based on what you have learned. Explain aloud why you are asking it and inspect the cited files, command output or diff yourself.

1. Understand the problem

Convert the ticket into acceptance criteria

Do not inspect or edit code yet. Rewrite the task as explicit acceptance criteria. Separate confirmed requirements, ambiguous points, reasonable assumptions and questions I should ask the interviewer. Identify security or backward-compatibility implications without inventing hidden requirements.

Explain an unfamiliar stack briefly

I am comfortable with software design but less familiar with this language/framework. Explain only the repository conventions I need for this task: entry point, routing, validation, service/domain logic, persistence, error handling and tests. Use examples from this repository, cite the files and avoid a general tutorial.

2. Map the repository without editing

Trace the execution path

Do not modify any files. Trace the current execution path for <feature or bug> from request/UI entry point through validation, controller/handler, service/domain logic, persistence and error response. Return an ordered call flow with file paths and symbols. Mark anything you inferred rather than directly verified.

Find conventions and relevant tests

Do not edit. Find the closest existing feature with similar validation or error handling. Show which project conventions it establishes, which tests cover it and the exact commands used to run those tests. Recommend reuse only where the repository evidence supports it.

Establish the baseline

Inspect the README and build files. Tell me the minimum install, run and test commands for this repository. Then run only the relevant existing tests. Report command output faithfully and distinguish pre-existing failures from failures related to this task. Do not fix anything yet.

3. Plan the change

Smallest safe implementation plan

Do not implement yet. Propose the smallest change consistent with the existing architecture. Include: acceptance criteria; files and symbols to modify; files that should not need modification; validation/error behaviour; edge cases; tests; security concerns; assumptions; and rollback risk. Avoid new dependencies, broad refactoring and new abstractions unless you can justify them from repository evidence.

Challenge the planned placement

Review the proposed placement of this logic. Compare request-boundary validation, domain/service validation and persistence constraints. Explain which layer should be authoritative in this repository and why. Identify duplication or bypass risks. Do not edit code.

4. Implement a focused slice

Bounded Agent-mode implementation

Implement only the agreed change in <files/symbols>. Follow current naming, dependency injection, validation, error and testing conventions. Preserve public interfaces and response formats. Do not modify unrelated files, add dependencies, reformat whole files or create speculative abstractions. After editing, stop and show the diff before running broader changes.

One file at a time

Modify only <file> to implement <specific responsibility>. Do not change tests or any other file yet. Explain each changed block and the invariant it enforces. Stop after displaying the diff for this file.

5. Diagnose a bug

Root cause before patch

Do not edit immediately. Reproduce or trace the failure and identify the root cause using concrete runtime output, tests or code paths. Give me: observed behaviour, expected behaviour, first divergence in the flow, evidence, and the minimum safe fix. Distinguish root cause from symptoms and list alternative hypotheses you ruled out.

Investigate a failing test

Read the complete failing test output. Explain what failed, where the expected and actual behaviour diverged, and whether the failure is caused by the new change, an incorrect test assumption or an existing repository issue. Do not weaken assertions merely to make the test pass.

6. Generate and review tests

Targeted test matrix

Create a compact test matrix for the acceptance criteria. Include happy path, null/empty input, boundaries, malformed input, duplicates, error contract, update path and regression cases only where relevant. Identify whether each case belongs in a unit, integration or end-to-end test and why.

Add focused tests

Add the smallest set of tests that proves the new behaviour and protects the existing contract. Follow the current test style and fixtures. Do not create a new test framework or broad snapshot. Show how each test maps to an acceptance criterion.

Check tests that pass for the wrong reason

Review these tests skeptically. Look for false positives, missing assertions, mocks that bypass the changed logic, over-broad exception assertions, order dependence and cases that never reach the relevant branch. Do not modify code until I review your findings.

7. Review the diff

Senior reviewer pass

Act as a skeptical senior reviewer. Inspect only the current diff for correctness, architectural placement, security, error handling, backward compatibility, race conditions, test adequacy and unnecessary changes. For every concern, cite the file and line/symbol and describe a concrete failure scenario. Do not edit.

Scope-control pass

List every changed file and classify it as required, justified supporting change or unrelated. Flag dependency changes, generated files, formatting churn, debugging statements and public-interface changes. Recommend the smallest diff that still satisfies the task.

8. Prepare your explanation

Changed-file walkthrough

Summarize the final solution in execution order. For each changed file explain: what changed, why the responsibility belongs there, which requirement it satisfies, which test verifies it, and any remaining risk. Identify any code I may have difficulty defending.

Interviewer follow-up simulator

Act as the interviewer. Ask one follow-up at a time about architecture, edge cases, tests, security, backward compatibility and AI usage. Wait for my answer. Then challenge one assumption or trade-off before moving to a harder follow-up. Do not reveal the ideal answer until I commit.

Two-minute closing summary

Help me compress this work into a two-minute verbal summary covering: requirement; root cause or prior behaviour; files changed; architectural reasoning; tests actually run; what the AI helped with; what I verified or rejected; and remaining risk. Use only facts supported by the repository and command output.

Prompt anti-patterns

AvoidWhy it is weakReplace with
“Fix this entire app.”No scope, no visible judgment, likely large diff.Trace first; implement one agreed responsibility.
“Make all tests pass.”May weaken tests or hide pre-existing failures.Explain the exact failure and minimum correct fix.
“What should I do?”Delegates the engineering decision.Present your plan and ask the AI to challenge it.
“Refactor for best practices.”Repository context and interview scope are ignored.Follow current conventions and avoid unrelated changes.
“Is everything correct?”Invites generic reassurance.Ask for concrete failure scenarios with file evidence.
Practise these in sequence, but choose deliberately.
