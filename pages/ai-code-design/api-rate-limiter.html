Interviewer question - AI-enabled version

Interviewer
This Spring Boot repository has a permissive request filter and an unused RateLimiter interface. Extend it so each customer may make at most N requests to an endpoint during a configured window. The implementation must be deterministic in tests, safe under concurrent calls in one process, and expose enough information for a 429 response. Start with the simplest algorithm that satisfies the stated requirement and discuss distributed evolution separately.

What should I think about first?

Think
  1. Clarify the key. Customer, API key, IP, tenant, endpoint, HTTP method, or a composite key?
  2. Clarify burst semantics. A fixed window is easy but allows a boundary burst. Token bucket and sliding window solve different product needs.
  3. Inject time. Tests must not sleep or depend on the wall clock.
  4. Make check-and-increment atomic. A thread-safe map alone is insufficient if read and update are separate operations.
  5. Separate LLD from distributed HLD. First make the repository behavior correct. Redis, Lua, failover and multi-region are follow-ups unless required.
I will confirm the limit key, algorithm semantics, response contract and failure behavior. Then I will locate the existing filter and tests, capture allow, reject and reset behavior with an injected clock, implement the minimum atomic in-process limiter, and only after that explain how I would move the state to an atomic distributed store.

The interview implementation can stay in-process if that is the stated scope. Name the guarantee honestly and describe, rather than prematurely build, the distributed version.

Acceptance criteria

  • The first N requests for the same key in one window are allowed; request N+1 is rejected.
  • Requests for different customers or endpoints use independent counters.
  • At the next window boundary, the counter resets deterministically.
  • A decision includes allowed/rejected, remaining quota and retry-after information.
  • Concurrent calls for one key cannot admit more than N requests inside one JVM.
  • Tests use an injected/fake clock and never sleep.
  • Configuration rejects non-positive limit/window values.
  • Limiter integration follows existing authentication, response and logging conventions.
  • The implementation states its single-process scope and does not pretend to enforce a fleet-wide limit.

The requirement says N requests in a configured window and does not mention burst smoothing, so I will start with a fixed window and make its boundary behavior explicit. If the product needs a rolling limit or controlled bursts, I would switch to a sliding-window counter or token bucket through the same interface and add algorithm-specific tests.

Illustrative Java implementation

public final class FixedWindowRateLimiter implements RateLimiter {
    private final Clock clock;
    private final ConcurrentHashMap<LimitKey, WindowState> states =
            new ConcurrentHashMap<>();

    public FixedWindowRateLimiter(Clock clock) {
        this.clock = Objects.requireNonNull(clock);
    }

    @Override
    public RateLimitDecision allow(LimitKey key, RateLimitPolicy policy) {
        if (policy.limit() <= 0 || policy.window().isZero()
                || policy.window().isNegative()) {
            throw new IllegalArgumentException("invalid rate-limit policy");
        }

        long nowMillis = clock.millis();
        long windowMillis = policy.window().toMillis();
        long startsAt = Math.floorDiv(nowMillis, windowMillis) * windowMillis;
        AtomicReference<RateLimitDecision> decision = new AtomicReference<>();

        states.compute(key, (ignored, current) -> {
            WindowState active = current == null || current.startsAt() != startsAt
                    ? new WindowState(startsAt, 0)
                    : current;

            if (active.used() >= policy.limit()) {
                Duration retryAfter = Duration.ofMillis(
                        startsAt + windowMillis - nowMillis);
                decision.set(RateLimitDecision.rejected(0, retryAfter));
                return active;
            }

            int nextUsed = active.used() + 1;
            decision.set(RateLimitDecision.allowed(
                    policy.limit() - nextUsed,
                    Duration.ofMillis(startsAt + windowMillis - nowMillis)));
            return new WindowState(startsAt, nextUsed);
        });
        return decision.get();
    }

    private record WindowState(long startsAt, int used) {}
}

public record LimitKey(String tenantId,
                       String customerId,
                       String endpoint) {}

public record RateLimitPolicy(int limit, Duration window) {}

public record RateLimitDecision(boolean allowed,
                                int remaining,
                                Duration retryAfter) {
    static RateLimitDecision allowed(int remaining, Duration retryAfter) {
        return new RateLimitDecision(true, remaining, retryAfter);
    }

    static RateLimitDecision rejected(int remaining, Duration retryAfter) {
        return new RateLimitDecision(false, remaining, retryAfter);
    }
}
Important scope and memory note

ConcurrentHashMap.compute makes the transition atomic for one key inside one JVM. It does not create a global limit across pods. The map also needs bounded lifecycle cleanup in a long-running service. Mention both before the interviewer has to ask.

Focused JUnit tests

class FixedWindowRateLimiterTest {
    private final MutableClock clock =
            MutableClock.at("2026-10-07T09:00:00Z");
    private final FixedWindowRateLimiter limiter =
            new FixedWindowRateLimiter(clock);
    private final RateLimitPolicy policy =
            new RateLimitPolicy(2, Duration.ofMinutes(1));
    private final LimitKey key =
            new LimitKey("tenant-a", "customer-1", "GET:/issues");

    @Test
    void allowsUpToLimitThenRejects() {
        assertThat(limiter.allow(key, policy).allowed()).isTrue();
        assertThat(limiter.allow(key, policy).allowed()).isTrue();

        RateLimitDecision rejected = limiter.allow(key, policy);
        assertThat(rejected.allowed()).isFalse();
        assertThat(rejected.remaining()).isZero();
        assertThat(rejected.retryAfter()).isPositive();
    }

    @Test
    void resetsAtNextWindowWithoutSleeping() {
        limiter.allow(key, policy);
        limiter.allow(key, policy);
        assertThat(limiter.allow(key, policy).allowed()).isFalse();

        clock.advance(Duration.ofMinutes(1));

        assertThat(limiter.allow(key, policy).allowed()).isTrue();
    }

    @Test
    void isolatesDifferentCustomers() {
        limiter.allow(key, new RateLimitPolicy(1, Duration.ofMinutes(1)));

        LimitKey other = new LimitKey(
                "tenant-a", "customer-2", "GET:/issues");
        assertThat(limiter.allow(other,
                new RateLimitPolicy(1, Duration.ofMinutes(1))).allowed())
                .isTrue();
    }
}

AI prompts for this question

Discovery - find the real integration point

Do not edit. Trace authentication, tenant/customer identity, endpoint normalization, the current request filter/interceptor, RateLimiter abstractions, policy configuration and error-response conventions. Find focused tests and all direct wall-clock calls. Report exact symbols, current behavior and the smallest insertion point. Do not propose Redis until the repository requirement proves a global limit is needed.

RED - limit boundary

Do not change production code. Add the smallest failing unit test using an injected or fake clock: for one key and a limit of 2 in one minute, calls 1 and 2 are allowed and call 3 is rejected with remaining 0 and positive retry-after. Run only this test, explain the failure, and stop.

GREEN - minimum atomic state transition

Implement only enough in-process fixed-window behavior to pass the focused test. Use the repository's existing interface and time abstraction. Make check-and-increment atomic per key; do not add Redis, queues, multiple algorithms or unrelated filter changes. Show the diff and run the focused test.

RED - deterministic reset and key isolation

Add failing tests that advance a fake clock across the window boundary without sleeping and prove that different customer/endpoint keys are independent. Preserve the existing response contract and run the tests before implementation.

Concurrency test and review

Design a deterministic test that starts more concurrent calls than the limit for the same key and asserts exactly N are allowed. Review the implementation for read-modify-write races, but do not introduce a global lock if a per-key atomic operation is available.

Distributed evolution - discussion only

Without editing code, explain how this exact decision contract would be implemented across many service instances using an atomic Redis operation or script. Cover key design, TTL, fail-open versus fail-closed, retry headers, policy caching and bounded inaccuracy during failover. Clearly separate this from the current in-process acceptance criteria.

Final skeptical review

Review the current diff as a P40 code-design interviewer. Check key correctness, window boundaries, injected time, atomicity, quota off-by-one errors, retry-after calculation, map growth, status/header integration, stated single-process guarantee, tests and unrelated edits. Cite concrete failure scenarios. Do not edit.

Likely P40 follow-ups

What is wrong with a fixed window?

A client can send N requests at the end of one window and N more at the start of the next, creating a 2N boundary burst. If that violates the product requirement, choose a token bucket or sliding-window approach and test the desired semantics.

How would you enforce the limit across many pods?

Move the mutable counter/refill state to a shared low-latency store and perform check plus update atomically, commonly with a Redis command sequence or Lua script. Keep the policy cached locally, define TTL and failover behavior, and monitor limiter latency/error rate.

Would you fail open or fail closed if the shared store is down?

It is a product/risk decision. For availability protection or abuse controls, fail-open can overload the backend. For a non-critical quota, fail-open may preserve customer availability. Sensitive endpoints may fail closed. State the choice per policy rather than globally.

How do you avoid unbounded in-memory keys?

Expire states after their window, run bounded cleanup, use a size-aware cache, or store only active keys with TTL. Also protect against attacker-controlled high-cardinality identities and normalize endpoint keys.

How would you support different plans and endpoints?

Resolve a policy using tenant/customer tier plus normalized endpoint/method. Cache policy separately from counters, version it, and define how an in-flight window behaves when a policy changes.

How do you return rate-limit information?

Use the repository's standard 429 error plus a retry duration/reset timestamp and remaining quota where appropriate. Do not leak sensitive policy details, and ensure gateway/proxy behavior does not overwrite the headers.

How would you test concurrency reliably?

Synchronize worker start with a barrier/latch, submit more calls than the limit, collect decisions, and assert exactly N successes. Run it repeatedly but avoid using timing sleeps as the assertion mechanism.

How would you support bursts?

Use a token bucket with capacity, refill rate, last-refill time and current tokens. The atomic transition calculates replenishment and then consumes one token. Inject time and test partial refill and capacity caps.

Common mistakes

  • Using System.currentTimeMillis() directly and sleeping in tests.
  • Using a concurrent map but performing a separate non-atomic get and put.
  • Returning only a boolean and forcing the filter to re-derive retry timing.
  • Ignoring key scope so one endpoint or tenant consumes another's quota.
  • Claiming an in-memory implementation is fleet-wide.
  • Adding Redis and distributed failure complexity before the local acceptance tests are green.
  • Forgetting stale-key cleanup or attacker-controlled key cardinality.
  • Letting AI choose an algorithm without first defining burst semantics.

Two-minute closing summary

I drove the change from deterministic tests: allow up to N, reject N+1, reset at a fake-clock boundary, isolate keys, and preserve exactly N admissions under concurrent calls. The first implementation is a fixed-window limiter because that matches the stated requirement, with an atomic per-key state transition and a decision object carrying remaining quota and retry timing. I integrated it at the existing authenticated request boundary and kept the guarantee honest: this version is correct within one JVM. For a fleet-wide limit, I would preserve the same contract and move the atomic state transition to Redis or another shared store, with explicit fail-open/fail-closed policy and TTL.
