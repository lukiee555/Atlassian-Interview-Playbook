Evidence boundary

The publicly reported requirement is that a Java banking application be extended so a credit-card PIN contains four distinct digits. The repository structure, API path, response contract and code below are a realistic practice reconstruction—not a disclosed Atlassian repository or hidden test suite.

Interviewer question

Interviewer
“Please extend this banking application so that a credit-card PIN contains exactly four distinct digits.”

What should I think about first?

Think
  1. Translate the phrase precisely. “Exactly four distinct digits” implies length four, ASCII digits only unless told otherwise, and no repeated digit.
  2. Do not model the PIN as an integer. A value such as 0123 may be valid and must retain its leading zero.
  3. Find every write path. New card creation, PIN change and PIN reset may each mutate the value.
  4. Find the existing authority. The repository may already have a validator, domain object, service or error-handling convention.
  5. Do not change storage/security casually. This ticket adds a business rule; preserve the application’s established secure storage mechanism unless the requirement says otherwise.
I understand the invariant as a four-character PIN containing only digits 0–9, with every character unique. I’ll confirm leading-zero and scope behaviour, then trace all create/update paths so the rule has one backend authority rather than being enforced only in one controller.

What the interviewer is looking for

  • You convert a short requirement into explicit acceptance criteria before asking AI to edit.
  • You inspect repository conventions and all mutation paths instead of guessing a file.
  • You preserve leading zeroes and reject non-ASCII characters deliberately.
  • You place the invariant in a reusable backend/domain location and optionally mirror it in the UI.
  • You add focused positive and negative tests, run them, and inspect the final diff.
  • You can explain why an AI-proposed abstraction is necessary—or why it is unnecessary.

Acceptance criteria

Approach
  • A PIN is valid only when it is non-null, length four, contains characters 0 through 9, and each digit appears once.
  • Leading zeroes are preserved.
  • Every in-scope PIN mutation invokes one authoritative policy.
  • An invalid PIN produces the existing validation error contract and does not persist a change.
  • Existing valid behaviour remains unchanged.

Implementation approach

The clearest implementation is a small stateless policy. A boolean[10] makes the ASCII and uniqueness rules explicit. Because the input length is fixed at four, runtime and extra space are effectively constant; described generally, the loop is O(n) time and O(1) space.

1. Authoritative PIN policy

package com.example.banking.cards;

import org.springframework.stereotype.Component;

@Component
public final class CreditCardPinPolicy {

    public void validate(String pin) {
        if (pin == null) {
            throw new InvalidPinException("PIN is required");
        }

        if (pin.length() != 4) {
            throw new InvalidPinException(
                    "PIN must contain exactly four digits");
        }

        boolean[] seen = new boolean[10];

        for (int index = 0; index < pin.length(); index++) {
            char current = pin.charAt(index);

            // Explicit ASCII check keeps the contract unambiguous.
            if (current < '0' || current > '9') {
                throw new InvalidPinException(
                        "PIN must contain digits only");
            }

            int digit = current - '0';
            if (seen[digit]) {
                throw new InvalidPinException(
                        "PIN digits must be distinct");
            }

            seen[digit] = true;
        }
    }
}
Why not convert to an integer?

Integer.parseInt("0123") becomes 123, losing information. The PIN is an identifier-like secret, not a quantity; String is the appropriate boundary model.

2. Existing domain exception

Prefer the repository’s current validation exception. This class is shown only to make the sample compile conceptually.

package com.example.banking.cards;

public final class InvalidPinException extends RuntimeException {
    public InvalidPinException(String message) {
        super(message);
    }
}

3. Service integration

package com.example.banking.cards;

import java.util.UUID;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CardService {
    private final CardRepository cardRepository;
    private final CreditCardPinPolicy pinPolicy;

    public CardService(
            CardRepository cardRepository,
            CreditCardPinPolicy pinPolicy) {
        this.cardRepository = cardRepository;
        this.pinPolicy = pinPolicy;
    }

    @Transactional
    public void changePin(UUID cardId, String requestedPin, UserId actor) {
        Card card = cardRepository.findById(cardId)
                .orElseThrow(() -> new CardNotFoundException(cardId));

        card.requirePinChangePermission(actor);
        pinPolicy.validate(requestedPin);

        // Preserve the repository's existing secure PIN-storage path.
        card.changePin(requestedPin);
        cardRepository.save(card);
    }
}

The order of authorization and validation can depend on the repository’s security/error policy. Do not leak information about a card the actor cannot access. Follow the existing convention and explain it.

4. Optional request-boundary feedback

If the project already uses Bean Validation, DTO checks can reject obvious shape errors early, while the domain policy remains authoritative for every mutation path.

public record ChangePinRequest(
        @jakarta.validation.constraints.NotNull
        @jakarta.validation.constraints.Pattern(
                regexp = "[0-9]{4}",
                message = "PIN must contain exactly four digits")
        String pin) {
}
Do not duplicate the uniqueness rule casually

A custom annotation is unnecessary unless the repository already uses that pattern or multiple boundaries need it. Keep the authoritative uniqueness policy in one reusable component.

Tests

Unit-test the invariant

package com.example.banking.cards;

import static org.junit.jupiter.api.Assertions.assertDoesNotThrow;
import static org.junit.jupiter.api.Assertions.assertThrows;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

class CreditCardPinPolicyTest {
    private CreditCardPinPolicy policy;

    @BeforeEach
    void setUp() {
        policy = new CreditCardPinPolicy();
    }

    @Test
    void acceptsFourDistinctDigits() {
        assertDoesNotThrow(() -> policy.validate("1234"));
    }

    @Test
    void preservesAndAcceptsLeadingZero() {
        assertDoesNotThrow(() -> policy.validate("0123"));
    }

    @Test
    void rejectsRepeatedDigits() {
        assertThrows(InvalidPinException.class,
                () -> policy.validate("1213"));
    }

    @Test
    void rejectsNull() {
        assertThrows(InvalidPinException.class,
                () -> policy.validate(null));
    }

    @Test
    void rejectsIncorrectLength() {
        assertThrows(InvalidPinException.class,
                () -> policy.validate("123"));
        assertThrows(InvalidPinException.class,
                () -> policy.validate("12345"));
    }

    @Test
    void rejectsNonAsciiDigitsAndOtherCharacters() {
        assertThrows(InvalidPinException.class,
                () -> policy.validate("12a4"));
        assertThrows(InvalidPinException.class,
                () -> policy.validate("12 4"));
    }
}

Common mistakes

  • Using an integer and accidentally losing leading zeroes.
  • Checking only pin.length() == 4 without uniqueness or digit validation.
  • Checking adjacent duplicates only, so 1213 incorrectly passes.
  • Adding validation only in the React form or one controller.
  • Trimming or normalizing secret input without an explicit requirement.
  • Adding a new validation framework or custom annotation for a four-line rule.
  • Changing storage/security code despite the ticket being limited to validation.
  • Asking AI for a broad refactor and accepting unrelated changes.
  • Testing the policy but never proving invalid input cannot persist through the real path.

Interviewer follow-ups

Why is the PIN a String rather than an integer?

It is not a numeric quantity and may start with zero. A String preserves representation, lets us validate each character explicitly and avoids numeric parsing edge cases.

Why do you need backend and frontend validation?

Frontend validation provides immediate feedback and avoids unnecessary requests. The backend is authoritative because clients can be modified, bypassed or outdated. I would mirror the rule in the UI only for user experience, while every backend mutation path invokes the domain policy.

Which file should contain this logic?

I would first follow the repository’s closest validation convention. The reusable invariant belongs in an existing domain validator/policy or service—not only in a controller. DTO validation can handle shape, and the controller should map transport concerns.

Could you use a Set or stream?

Yes. pin.chars().distinct().count() == 4 is compact after digit/length validation. A boolean array is explicit, allocation-light and easy to explain. At fixed length four, performance is irrelevant; readability and repository style decide.

What if the PIN length becomes configurable?

I would generalize only after that requirement exists: pass a policy configuration for length and allowed character set, validate that requested length cannot exceed ten when every digit must be distinct, and extend the tests. I would not add that abstraction pre-emptively.

What happens to existing invalid PINs?

That is a product/data decision. My default is to enforce the invariant on future create/change/reset operations without blocking reads. If migration is required, I would avoid exposing or auto-transforming secrets and work with the existing secure reset process.

How do you ensure every update path uses the rule?

I trace all public mutation paths and put validation in the shared service/domain method that owns the state transition. I add at least one test for each distinct bypass risk, and I search for direct setters or repository writes.

What if two PIN-change requests arrive concurrently?

Uniqueness within a PIN is unaffected, but last-write behaviour matters. I would follow the existing concurrency model—often an entity version with optimistic locking. A stale update can return a conflict instead of silently overwriting a newer change.

Would you expose a detailed validation message?

For a new PIN policy, actionable messages can improve UX, but I would preserve the repository’s security and API conventions. Authentication errors generally need less detail than input-policy errors.

How many possible PINs satisfy the rule?

If leading zeroes are allowed, there are 10 × 9 × 8 × 7 = 5,040 ordered four-digit strings with no repeated digit. This is a product/security implication worth raising if the interviewer wants to discuss entropy, but it does not change the requested validation.

What I would say after implementation

I traced the create and PIN-change flows and placed one authoritative rule in the existing domain-policy layer. The PIN remains a String so leading zeroes are preserved. The validator explicitly checks null, exact length, ASCII digits and duplicates. I reused the current exception mapping and secure storage path, added focused policy tests plus an integration check that invalid input is not persisted, ran the relevant suite and reviewed the diff for unrelated changes. The AI helped map the repository and draft tests; I verified the cited paths and rejected broader refactoring.

Question-specific AI prompts

Find every PIN mutation path

Do not edit. Find every path that creates, changes, resets or persists a credit-card PIN. Produce an ordered call graph with file paths and symbols. Identify any path that would bypass validation added only to the primary controller.

Challenge the edge cases

Review the requirement “exactly four distinct digits.” List all materially different edge-case classes, including representation, character set, duplicates and update behaviour. Do not invent product requirements; mark questions versus assumptions.

Review the final PIN diff

Inspect the current diff only. Check leading-zero preservation, ASCII digit handling, non-adjacent duplicates, null/empty input, validation bypasses, unchanged API/error contract, unchanged secure storage, test discovery and unrelated edits. Cite a concrete failure scenario for every concern.
