Evidence boundary

Several public P40 or P40/P50 reports describe a middleware router or dynamic route-mapping exercise with addRoute/getRoute, wildcard path segments, Trie discussion, and scalability follow-ups. The exact wildcard direction differs across retellings. This page therefore makes that ambiguity an explicit clarification and turns the family into an existing-repository, TDD-first AI exercise. It is not presented as a leaked current HackerRank prompt.

Interviewer question - AI-enabled version

Interviewer
This repository contains an exact-match middleware router. Extend it so callers can register patterns containing a single-segment wildcard and resolve request paths deterministically. Exact routes must take priority over wildcard routes, duplicate registration must follow the existing contract, and the public API must remain compatible. Use tests to drive the change and use the AI assistant deliberately.

What should I think about first?

Think
  1. Clarify wildcard semantics. Is * allowed in the registered pattern, the lookup query, or both? Does it match one segment or the rest of the path?
  2. Define precedence before data structure. Exact over wildcard is common, but registration order, named parameters, and catch-all behavior must be explicit.
  3. Preserve the existing contract. Duplicate registration, trailing slashes, URL decoding, query strings, and not-found behavior may already be tested.
  4. Choose a structure from access patterns. A list scan is simplest for a tiny route set. A segment Trie gives O(number of segments) lookup and clean precedence.
  5. Make the first change narrow. Add one wildcard behavior and its tests before introducing named parameters, removal, or thread safety.
I will first confirm where wildcards appear, whether they match one segment or the remaining path, and how ties and duplicate registrations should behave. Then I will inspect the existing exact-match tests, establish a baseline, add the smallest failing wildcard test, implement the minimum compatible change, and add precedence and normalization edge cases before reviewing complexity and concurrency.

Acceptance criteria

  • All pre-existing exact routes resolve exactly as before.
  • A registered * matches exactly one path segment.
  • An exact segment wins over a wildcard at the same depth.
  • A wildcard does not match a missing segment or two segments.
  • Path normalization follows the repository's established slash policy.
  • Duplicate registration follows the existing contract and is tested.
  • Not-found behavior and public API shape remain compatible.
  • Lookup is O(S) for an unambiguous Trie path, where S is the number of segments; bounded branching is explained if supported.
  • Focused and exact-route regression tests pass; no unrelated framework refactor is included.

Illustrative Java design

public final class RouteRegistry<T> {
    private static final String WILDCARD = "*";
    private final Node<T> root = new Node<>();

    public void addRoute(String pattern, T value) {
        Objects.requireNonNull(value, "value");
        Node<T> current = root;
        for (String segment : segments(pattern)) {
            if (WILDCARD.equals(segment)) {
                if (current.wildcard == null) {
                    current.wildcard = new Node<>();
                }
                current = current.wildcard;
            } else {
                current = current.exact.computeIfAbsent(
                        segment, ignored -> new Node<>());
            }
        }
        // Practice contract: registering the same pattern replaces its value.
        current.value = value;
    }

    public Optional<T> getRoute(String requestPath) {
        return match(root, segments(requestPath), 0);
    }

    private Optional<T> match(Node<T> node,
                               List<String> parts,
                               int index) {
        if (index == parts.size()) {
            return Optional.ofNullable(node.value);
        }

        String segment = parts.get(index);
        Node<T> exact = node.exact.get(segment);
        if (exact != null) {
            Optional<T> result = match(exact, parts, index + 1);
            if (result.isPresent()) {
                return result;
            }
        }

        if (node.wildcard != null) {
            return match(node.wildcard, parts, index + 1);
        }
        return Optional.empty();
    }

    private List<String> segments(String rawPath) {
        if (rawPath == null || rawPath.isBlank()) {
            throw new IllegalArgumentException("path must not be blank");
        }
        return Arrays.stream(rawPath.split("/+"))
                .filter(part -> !part.isBlank())
                .toList();
    }

    private static final class Node<T> {
        private final Map<String, Node<T>> exact = new HashMap<>();
        private Node<T> wildcard;
        private T value;
    }
}
Illustrative, not a forced architecture

In the actual interview, preserve existing classes, path parser and error contract. If the repository already uses an ordered route list, a small tested extension may be safer than replacing it with a Trie during a one-hour round.

Focused JUnit tests

class RouteRegistryTest {
    private final RouteRegistry<String> routes = new RouteRegistry<>();

    @Test
    void wildcardMatchesExactlyOneSegment() {
        routes.addRoute("/teams/*/issues", "team-issues");

        assertThat(routes.getRoute("/teams/alpha/issues"))
                .contains("team-issues");
        assertThat(routes.getRoute("/teams/issues")).isEmpty();
        assertThat(routes.getRoute("/teams/a/b/issues")).isEmpty();
    }

    @Test
    void exactRouteWinsOverWildcard() {
        routes.addRoute("/teams/*/issues", "generic");
        routes.addRoute("/teams/admin/issues", "admin");

        assertThat(routes.getRoute("/teams/admin/issues"))
                .contains("admin");
        assertThat(routes.getRoute("/teams/alpha/issues"))
                .contains("generic");
    }

    @Test
    void duplicateRegistrationUsesCurrentReplacementContract() {
        routes.addRoute("/health", "v1");
        routes.addRoute("/health", "v2");

        assertThat(routes.getRoute("/health")).contains("v2");
    }

    @Test
    void normalizesRepeatedAndTrailingSeparators() {
        routes.addRoute("/teams/*/issues/", "handler");

        assertThat(routes.getRoute("//teams//alpha//issues//"))
                .contains("handler");
    }
}

Add separate failing tests proving that an exact route wins over an overlapping wildcard route and that path normalization follows the current repository contract. Do not weaken or rewrite existing tests. Run the new tests and explain each failure before implementation.

Likely P40 follow-ups

How would you add named parameters such as :teamId?

Add a parameter child distinct from the wildcard child, capture the consumed segment into a parameter map, and define precedence such as exact > named parameter > wildcard. Ensure only one parameter child exists at a node regardless of parameter name, or explicitly define conflict behavior.

How would you support a catch-all route?

Use a separate catch-all edge that consumes zero or more remaining segments and is evaluated after exact, parameter and single-segment wildcard branches. Because this creates more ambiguity, define whether it must be terminal and test precedence explicitly.

What if multiple wildcard patterns match?

Do not use registration order accidentally. Define specificity rules: more exact segments, then fewer wildcards, then an explicit stable tie-breaker or reject ambiguous registrations. A compile-time ambiguity check can keep lookup simple.

How would you make registration and lookup thread-safe?

If routes are built at startup and then read, publish an immutable snapshot. If live registration is required, use copy-on-write snapshots or a read-write lock around mutation; avoid holding a global lock on every lookup. The choice depends on update frequency and language/runtime.

How would you support route removal?

Clear the terminal handler, then prune empty nodes bottom-up only when they have no value and no children. Test that removing one route does not delete a shared prefix.

Why not compile every route to regex?

Regex is viable for a small route set, but it makes precedence and escaping less transparent and usually requires scanning every pattern. A segment Trie maps directly to the domain and keeps common lookup proportional to path length.

How would you include HTTP method or host?

Make them part of the routing key or a first-level index, for example method -> host -> path Trie. Preserve method-specific 404/405 semantics rather than treating everything as one path namespace.

What should happen with URL-encoded slashes?

Clarify where decoding occurs. Decode exactly once in a trusted boundary and avoid converting an encoded slash into a new path segment unexpectedly. Reuse the framework parser rather than hand-rolling security-sensitive URL decoding.

Common mistakes

  • Implementing a Trie before defining whether wildcard is registered or queried.
  • Letting wildcard precedence depend on hash-map or registration iteration order.
  • Making * match zero, one and many segments in different paths.
  • Breaking exact-route behavior or the existing not-found/error contract.
  • Normalizing paths differently in addRoute and getRoute.
  • Adding named params, catch-all routes, methods, hosts and middleware chains before the first test is green.
  • Accepting an AI-generated full rewrite without comparing the diff to the narrow requirement.

Two-minute closing summary

I preserved the existing exact-route contract and added a one-segment wildcard through tests first. The matching semantics are explicit: normalized path segments, exact branch before wildcard fallback, and no match when path length differs. I chose the existing structure if it remained simple; otherwise a segment Trie keeps common lookup proportional to path length and makes precedence visible. I ran exact-route regression tests, reviewed the diff for normalization and duplicate behavior, and left named parameters, catch-all matching and concurrent updates as clearly scoped follow-ups rather than speculative code.
